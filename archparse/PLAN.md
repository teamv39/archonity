## 2. Блоки работ

### Блок 0. Измерение [ВЫПОЛНЕНО 17.10.2026]

- Журнал решений пишет сам `GraphBuilder` (`engine/decisions.py`), прогон сохраняет его в `output/decisions.json`. Журнал совпадает с ответом ребро в ребро, это проверяет тест.
- `scripts/decision_log.py` только читает журнал. Список риска A: рёбра ответа, включённые одной достижимостью скелета (S2: 264 ребра в 127 методах, S3: 229 в 114). Список риска B: рёбра, срезанные `rules.py`, со строкой сработавшего правила (S2: 18, S3: 8).
- Расширение пула до 52 методов выдачу не изменило: новые ветки либо «ошибка, ранний выход», либо G/D-диспатч, который уже решали правила по `train_mode`.

### Блок 7. Ленивые коллекции JPA (R10) [ВЫПОЛНЕНО 17.10.2026, подтверждено платформой]

Итог: минус 17 рёбер `data` в S1–S7, S0 = 1.0000. Платформа: 0.91709 против 0.90208 (+0.0150). Подробности: FINDINGS, раздел 5.

Скелет даёт вызову репозитория таблицы коллекций (`route_stations`, `route_distances`, `train_food_list`, `user_roles`) в `data_access`. Движок выдаёт их всегда, когда вызов исполнился. По README и R10 таблица коллекции идёт в ответ, только если коллекция загрузилась, пока метод на стеке. Ленивая коллекция, которую метод только вернул, грузится позже, при сериализации ответа, и в ответ не идёт. Прецедент в S0: у `loadUserByUsername` в `data_access` есть `user_roles`, в эталоне нет.
