# ADR-007: Профиль проекта и виды ссылок шагов

## Статус

**Принят 20.10.2026.** Решения 1, 4 и порядок работ (7) принял пользователь 20.10, остальные — как предложены. Удалять ли режим `v7` после переключения умолчания — решаем по итогам фазы B2. Дополняет [ADR-005](adr-005_scenario_execution_pipeline.md) (M1, M4, контракт `StepRequest.refs`). Сценарий правок — [two_stage_pipeline_research.md](../researches/two_stage_pipeline_research.md), что подогнано — [universality_audit_after_1_0.md](../researches/universality_audit_after_1_0.md).

## Контекст

В M1 и M4 зашит домен Train Ticket. Выдача кода при этом даёт 1.00000 (sha256 `94463c41…5a08`), и её нужно сохранить: сдача 22.10, после 21.10 — только правки под флагом.

Что зашито в M1 (`engine/grounding/`):

- `prompts.SYSTEM`: «Train Ticket web application», правило близнецов про GaoTie/DongChe и обычные поезда, `ts-ui-dashboard`, `/api/v1/<service>/`.
- `prompts.PARAMS_TASK`: перечень полей бронирования («seat class, food, assurance, consignment weight and consignee»).
- `prompts.train_kind()`: строка в карточке близнеца «serves high-speed trains (GaoTie/DongChe, G/D) only».
- `request.REF_ENTITIES`: 12 видов ссылок Train Ticket, входят в JSON-схему ответа `select`.
- `text.DOMAIN_SYN` (consignment, luggage → consign; account → user) — BM25.
- `embedder.QUERY_TASK`: «train ticket booking web app».
- `ui_catalog.UI_DIR = "ts-ui-dashboard"`.

Что зашито в M4 (`engine/executor/`):

- `schema._DEFAULT_KIND_HINTS`, `_DEFAULT_ID_FIELDS` — 12 видов с ID-полями, `_USER_FIELDS` (`accountId`, `userId`, `loginId`).
- `step.build_dto`: `m4-new-user`, `m4-new-contact-doc`, `m4-new-companion`, `13800000000`, `consignee`/`consignee-phone`.

Что есть для замены:

- Скелет: аннотации типов (`@Entity` — 27 классов с 22 простыми именами, `@Embeddable` — `Food`) и полей (`@Id`, `@EmbeddedId`, `@Table`), поле `context` организаторов (шлюз, пассажир, «no verification code at login»).
- Каталог UI: условия, по которым UI выбирает близнеца. `preserveOther` уходит при `!(tripType == 'G' || tripType == 'D')`, поиск рейсов — по `train_type == 1` / `== 2`. В README Train Ticket о близнецах ничего нет.
- `twin_markers` / `twin_groups` (`retrieval.py`, с feature/84) — пары близнецов из совпадения API модулей.
- Кеш LLM — sha256 от полного текста сообщений и схемы (`engine/grounding/llm.py`). Любая правка промпта или схемы — промах на всех 173 вызовах M1. Пересборка: 103 `select` + 70 `params`, 503 с при `-ncmoe 7`, около 15 минут при `-ncmoe 11–12`.
- Офлайн-проверка M1: `python -m engine.grounding.grounder --eval eval/m1_steps.json` (top-1 и параметры) и `scripts/compare_submissions.py` с рекордом.

Связь M1 и M4 одна — имена видов в `StepRequest.refs`. Остальное (`handler`, `http`, `params`, `expected_outcome`) от домена не зависит.

## Решения

### 1. Промпт M1: общий шаблон и пересборка кеша

- **А. Байт в байт** (research, раздел 4): профиль Train Ticket пишется руками так, чтобы промпт совпал с `m1-v7`. Кеш цел, риска нет, но текст про поезда просто переезжает из кода в JSON.
- **Б. Общий шаблон** без слов домена, домен и правило близнецов — из профиля, который пишет LLM-профилировщик (решение 4). Новая `PROMPT_VERSION = "m1-v8"`, кеш пересобирается на GPU.

**Решено 20.10: Б.** Режим `m1-v7` остаётся флагом отката (решение 6).

### 2. Виды ссылок

Вид — имя типа, который хранит JPA: класс с `@Entity` или `@Embeddable`, простое имя с первой строчной буквой (`TrainType` → `trainType`). Классы с одним простым именем в разных модулях (`Order` в `ts-order-service` и `ts-order-other-service`, `Trip`, `User`, `Money`, `Payment`) — один вид; конкретный класс M4 выбирает по модулю шага, как сейчас по имени типа. В Train Ticket видов 23.

Соответствие видов v7:

| v7 | v8 | Примечание |
|---|---|---|
| `trip`, `order`, `station`, `route`, `assurance`, `user`, `food` | те же | `food` — `@Embeddable` `Food` |
| `contact` | `contacts` | |
| `price` | `priceConfig` | |
| `consign` | `consignRecord` | |
| `store` | `stationFoodStore` | в выдаче v7 не встречается |
| `train` | `trainType` или `trip` | v7 смешивает: S6.5, S6.6 — тип поезда (`new_of_step_3`), S4.6, S7.10 — рейс из поиска |

ID-поля вида — забота M4, M1 их не видит. Принцип: поле `@Id`, если оно не `id`; затем `<вид>Id` (`trainTypeId`, `contactsId`); затем `id`. Точный порядок и состав сессия M4 подбирает так, чтобы выдача совпала с рекордом (sha256).

Значение ссылки не меняется: `<first|second|new>_of_step_<n>`.

### 3. Манифест сущностей

Новый модуль `engine/manifest.py` — факты о сущностях из скелета, без LLM и без `archparse`. Не внутри `executor/` и `grounding/`: его читают оба.

```python
@dataclass(frozen=True)
class EntityKind:
    kind: str                      # "trainType"
    types: tuple[str, ...]         # FQN классов с этим простым именем
    id_fields: tuple[str, ...]     # по решению 2
    tables: tuple[str, ...]        # ID узлов таблиц из @Table или имени класса

def entity_kinds(ix: SkeletonIndex) -> dict[str, EntityKind]: ...
```

M4 (`EntitySchema`) берёт отсюда виды и ID-поля, M1 — список видов для схемы `select`. `engine/entities.py` (факты `archparse` для R7, R10) не трогаем.

### 4. Профиль проекта (Stage 0)

Профилировщик — один вызов LLM через `LLMClient`, вид `profile`, своя версия промпта `profile-v1`. Ответ кешируется в `cache/llm/`, как любой другой.

Вход:
- начало README проекта;
- `context` скелета;
- модули и виды из манифеста;
- пары близнецов (`twin_groups`) и условия UI, при которых UI шлёт запрос в каждую сторону.

Выход — JSON по схеме:
- `domain_summary` — одно-два предложения о системе;
- `twin_rules` — на каждую пару близнецов: какие данные обслуживает каждая сторона, по какому признаку шага выбирать.

Что не от LLM, а из кода и скелета: шлюз и окружение (`context`), модуль UI, виды, пары близнецов.

Где хранится:
- **А.** `data/project_profile.json` — источник правды, M1 читает файл. Файл можно поправить руками, и это никто не заметит.
- **Б.** M1 при сборке строит профиль сам: тот же вызов `LLMClient`, из кеша — тот же ответ. `data/project_profile.json` — копия для чтения, конвейер её не читает.

**Решено 20.10: Б.** Профиль на защите — ответ модели, а не текст, который мы написали; правка руками ломает ключ кеша и видна. Если сервера и кеша нет, профиль пустой, и промпт идёт без описания домена и правил близнецов. Рукописный профиль (А) не нужен и как запасной: откат — режим `v7`.

Итерации, если профиль вышел плохим, — правкой промпта профилировщика (общего), а не текста профиля.

### 5. Что уходит из кода M1 и куда

| Сейчас | v8 |
|---|---|
| описание Train Ticket в `SYSTEM` | `domain_summary` профиля |
| правило близнецов в `SYSTEM`, `train_kind()` в карточке | `twin_rules` профиля, в карточке — правило своей пары |
| шлюз `/api/v1/<service>/` | `context` скелета |
| `ts-ui-dashboard` в `SYSTEM` и `UI_DIR` | модуль UI из `targets` (каталог с JS-страницами без Java) |
| перечень полей в `PARAMS_TASK` | общая формулировка: поля, значение которых следует из текста шага |
| `REF_ENTITIES` | виды из манифеста (решение 2) |
| пример `refs` в `SELECT_TASK` (`trip`, `order`) | пример из видов манифеста или без имён видов |
| `DOMAIN_SYN` | убрать из пути M1: синонимы — работа эмбеддера. `resolver.py` (legacy) не трогаем |
| `QUERY_TASK` про train ticket | общий: «user action in a web application» |

Правку `QUERY_TASK` нужно пересчитать: меняются векторы запросов (документы — нет), эмбеддер с сервером LLM в видеопамять не помещается — считать при остановленном сервере или на CPU. Без `DOMAIN_SYN` меняются ранги BM25: перепроверить MR-3 в `tests/test_metamorphic.py`.

### 6. M4: значения тела запроса

По research, раздел 5.2. Скоуп сессии M4 (решено 20.10): манифест, `EntitySchema`, `build_dto`. Не трогаем: `_FIELD_ALIASES`, нормализацию строк при повторе шага, `_is_failure`.

- Поле, по которому создающий метод ищет дубликат (`findBy<Поле>` перед `save` в IR), получает значение, которого нет в мире БД.
- Значение, записанное шагом, переиспользуется следующими (имя при регистрации → вход).
- Пустой код подтверждения при входе — из `context` скелета («no verification code at login»).
- Получатель багажа — из условных значений UI (`body_cond` каталога), если это обобщается; иначе — оставить с обоснованием в `annotation_rules.md`.
- Текущий пользователь: сейчас его ID берётся из ответа входа по типу `TokenDto` (подсказка вида `token`), а поля, куда он идёт, — список `accountId`, `userId`, `loginId`. Открытый вопрос для сессии M4. Кандидаты: шаг входа — тот, где исполнился `AuthenticationManager.authenticate` (как Spring Security с feature/84); поля — по потоку данных UI (`sessionStorage.setItem("client_id", …)` при входе → `accountId: sessionStorage.getItem("client_id")` в теле). Не найдётся общего правила — оставить список с обоснованием.

Пока жив режим `m1-v7`, M4 понимает и виды v7: словари `_DEFAULT_*` остаются как совместимость с v7, привязанная к этому режиму явно.

### 7. Флаг, откат и порядок работ

```text
run_eval.py --m1-prompt ...
  v8 — общий шаблон, профиль, виды из манифеста (по умолчанию, если выдача = рекорд)
  v7 — промпт и виды до ADR-007, кеш m1-v7; для отката
```

Умолчание переключается на `v8`, только если выдача совпала с рекордом ребро в ребро. Если нет — дифф рёбер к пользователю, решаем вместе. Если совпала, режим `v7`, его тексты, кеш `m1-v7` и совместимость M4 с видами v7 удаляются в том же PR (рекомендация).

**Порядок работ (решено 20.10):** в каждой фазе меняется одна переменная и сверяется с неподвижной базой.

| Фаза | Сессия | Что меняется | База |
|---|---|---|---|
| A | новая, без GPU | M4: манифест, `EntitySchema`, `build_dto` | кеш M1 `v7` → sha256 рекорда |
| B1 | M1, GPU | промпт, профиль, эмбеддер; виды прежние | M4 из `dev` → рёбра рекорда, `m1_steps.json` |
| B2 | M1, после мержа A | виды ссылок v8 | M4 из A → рёбра рекорда |

A и B1 идут параллельно, в своих worktree; файлы не пересекаются, кроме флагов `run_eval.py` и доков.

## Критерии приёмки

1. Фаза A: `python run_eval.py --no-server` — sha256 рекорда. Контрфакт: обёртка переписывает `refs` выдачи v7 на виды v8 (таблица решения 2, `train` — по смыслу шага) — рёбра рекорда.
2. Фаза B1: точность `--eval eval/m1_steps.json` не ниже v7; выдача — рёбра рекорда.
3. Фаза B2: выдача с умолчаниями — рёбра рекорда; прогон из кеша без сервера в чистом worktree воспроизводит sha256.
4. В `engine/grounding/` и `engine/executor/` при умолчаниях нет имён Train Ticket (кроме режима `v7`, если он остался).
5. Тесты зелёные, кроме известных ([environment_guide.md](../environment_guide.md), разделы 3 и 9).

## Последствия

- Домен приходит в M1 из ответа модели и фактов скелета, в M4 — из скелета. На защите: «словари и правила близнецов не пишем руками».
- Это не доказывает работу на другом проекте: эталона там нет. Проверяемо только косвенно — метаморфные тесты, ручной разбор пары сценариев. Фразу «на любом проекте без правки кода» без этого не говорить (research, раздел 5).
- Остаётся специфика, которую профиль не снимает (research, раздел 7): R20 `rebind`, `_FIELD_ALIASES`, нормализация строк при повторе шага, `*.Response`, промпт судьи (по умолчанию выключен). При пересборке кеша в фазе B2 можно убрать несвязываемый обработчик из каталога M1 (аудит, 2.1.1) и проверить выбор модели на шаге 4 S2/S3; ошибается — `rebind` остаётся.
