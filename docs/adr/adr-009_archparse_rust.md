# ADR-009: archparse на Rust

## Статус

**Принят 22.10.2026** (Денис). Предложен 21.10.2026, реализован в PR #126. Платформа 22.10 дала скор 1.0 на архиве с Rust-движком и Rust-разбором. Проверка на собственных сценариях X1–X8: `--engine python` и `--engine rust --parse-sources` дают одинаковые `submission.json`, `decisions.json`, `evidence.json`, `m4_unknowns.json`, `step_requests.json` (у X1–X8 нет ответов LLM в кеше, M1 в режиме `emergency`, сверка относится к M4 и разбору). Продолжает [ADR-008](adr-008_rust_engine_boundary.md): там `archparse` оставлен на Java «до отдельного решения»; 21.10 Денис решил переносить разбор кода целиком. Java-версия остаётся эталоном и оракулом, не удаляется.

## Контекст

Надбавка ×1.10 за Rust даётся за анализ кода, а тонкая обёртка вокруг Java-программы её не даёт. Весь `engine/` уже на Rust; разбор исходников (`archparse/`, 19 файлов, около 3.3 тыс. строк в `src/main`) остаётся на Java. Он строит `data/ir/<module>.json` (42 файла, 5.2 МБ) и `data/entity_ir.json` (273 вызова репозиториев, 28 сущностей, 25 конструкторов).

## Что реально использует archparse из JavaParser

Главный риск задачи — резолв символов, которого у `tree-sitter` нет. Проверка кода (`grep` по `SymbolSolver`, `resolve()`, `calculateResolvedType`, `ParserConfiguration`) показала: **JavaSymbolSolver не используется нигде**. JavaParser работает как чисто синтаксический парсер. Всё «знание о типах» — свои индексы:

| Что | Где в Java | Чем заменяем в Rust |
|---|---|---|
| тип по простому имени: импорт, пакет, `*`-импорт, модуль, зависимости модуля | `ProjectIndex.resolveType` | порт 1:1 на индекс типов проекта, зависимости из `depends_on` скелета |
| константы enum, `static final` с литералом | `ProjectIndex`, `EnumResolver` | порт 1:1 |
| `ref` имени: параметр, локальная, поле, тип, статический импорт | `BodyIrBuilder` (стеки областей) | порт 1:1, чисто лексически |
| привязка вызова к `call_site` и `target` | `SkeletonGraph` по `(file, line, col в байтах UTF-8)` и `uniqueMethod` | порт 1:1; колонка в байтах приходит из tree-sitter напрямую (`start_position().column + 1`) |
| сущность репозитория, переменные «типа сущности» | `EntityScanner` (строки типа, `declaredTypes`) | порт 1:1: сопоставление по тексту объявленного типа, без вывода типов выражений |

`TypeIndex.java` — мёртвый код (на него никто не ссылается), не переносим. `TargetPool` и `AstAnalyzer` удалены раньше.

## Решения (предложения)

1. **Парсер: `tree-sitter` + `tree-sitter-java`**, новый crate `rust/crates/archonity-parse`, бинарник `archonity-parse` (режимы `--mode bodies|entities|all`, флаги как у Java: `--targets-dir`, `--skeleton`, `-o`). Скелет читается своим кодом на `serde_json` (не через `archonity-io`: тот нужен движку, а разбору хватает карт call_site/методов/типов/зависимостей).
2. **Тонкий слой над tree-sitter** (`ast.rs`), без отдельного AST: логика `BodyIrBuilder`/`EntityScanner` портирована построчно на узлы tree-sitter, а различия с JavaParser спрятаны в помощниках (условие `if` без скобок оператора, «логический родитель» без `argument_list`, объявления полей в интерфейсах как `constant_declaration`, список операторов без комментариев, `;` как пустой оператор только для подсчёта).
3. **Печать выражений и типов как JavaParser.** Важная находка: `Type.asString()` печатает аргументы обобщений через `,` без пробела (`Map<String,String>`), а `toString()` pretty-printer — через `, `. Нужны обе формы (`type_str` и `type_pretty`). Оригинал кладёт в выдачу тексты, полученные его pretty-printer: `id` циклов `foreach` (`f390:trMap.entrySet()`), `*_reason` в `entity_ir.json` (`if (a != null && !a.isEmpty())`, `new Config(a, b)`), `method_ref`, `receiver` у конструкторов, `asString()` типов (`Map<String, List<Order>>`). Пишем свой печатник выражений и типов в стиле JavaParser (пробелы вокруг операторов, `, ` между аргументами, обобщения нормализованы). Он нужен только для выражений, которые реально попадают в артефакты; остальное печатаем тем же кодом, но сверка идёт по данным.
4. **Запись JSON как Jackson `INDENT_OUTPUT`.** Формат не Python (`"k" : v`, `[ {`, `} ]`, пустые `[ ]` и `{ }`, массив скаляров в одну строку). Свой писатель по `serde_json::Value` с `preserve_order`; числа `double` — как `Double.toString` Java.
5. **Сверка байт в байт с `data/`.** Эталон — файлы в git. JDK на машине разработки нет (Gradle недоступен), поэтому пересборка Java нужна только для спорных случаев; тесты `cargo test` и `pytest tests/test_rust_parse.py` сравнивают вывод Rust с `data/` побайтно.
6. **Интеграция.** `scripts/run_final.sh` после сборки запускает `archonity-parse` в `data/` (или `--artifacts-dir`), если артефактов нет или `engine/artifacts.py` находит их несвязанными со скелетом; сообщение `ArtifactMismatch` указывает команду Rust, а не `gradlew`. Отката на Java при сбое Rust нет.

## Риски

- **Pretty-printer JavaParser.** Любое расхождение в формате печати меняет `id`/`reason`. Смягчение: печатник проверяется на всех местах артефактов, где такой текст есть.
- **Порядок и дубли в `EnumResolver`.** Состояние статическое, перечисления регистрируются несколько раз (`scanEnums` по всем `.java`, затем `parseAll`), при неоднозначном простом имени берётся первый кандидат в порядке обхода файловой системы. Ограничение: порядок обхода у Java зависит от ФС; в Rust берём отсортированный и проверяем, что результат не меняется на данных проекта.
- **Расхождения грамматик.** tree-sitter терпим к ошибкам и по-другому группирует узлы (switch, лямбды, аннотации, `var`); неподдерживаемые узлы дают `op: unsupported`/`text`, как у оригинала, и сверка покажет их сразу.
- **Литералы.** `Double.toString`, `char`/строки с эскейпами, текстовые блоки.
- **Пути.** Порядок `Files.walk` (сортировка путей) и разделители `/`.

## Что не делаем

Не меняем контракты IR ([archparse/README.md](../../archparse/README.md), разделы 3.5–3.6) и ID из скелета. Java-версию не удаляем и из `run_final.sh` не запускаем.

## Результат реализации

Проверено на пакете Train Ticket (532 файла `src/main/java`, скелет `trainticket.json.gz`):

| Артефакт | Результат |
|---|---|
| `data/ir/*.json` (42 файла, 1196 методов, 8961 call_site) | байт в байт; покрытие скелета полное: 0 пропущенных методов, 0 неразобранных объявлений, 0 непокрытых и лишних call_site |
| `data/entity_ir.json` (28 сущностей, 273 вызова репозиториев, 25 конструкторов) | байт в байт |
| `run_eval.py --engine rust --parse-sources --artifacts-dir <новая папка>` | sha256 выдачи `94463c41…5a08` (рекорд) на артефактах, построенных Rust |

Время разбора около секунды (Java: около 10 с). Сверка воспроизводима: `pytest tests/test_rust_parse.py`, `cargo test -p archonity-parse`.

Отклонения от черновика и допущения (предложения, ждут решения Дениса):

- JDK на машине разработки не было, Java-версию не пересобирали: оракул — закоммиченные артефакты. Их построила Java-версия 21.10 (файлы в git, `tests/test_method_ir.py`, `tests/test_entities.py`).
- Порядок обхода файлов: Rust сортирует относительные пути побайтно; Java сортирует `Path` (на Windows без учёта регистра). На данных проекта результат одинаков; на проекте с одинаковыми простыми именами enum в разных не общих модулях порядок кандидатов в `EnumResolver` мог бы отличаться (у Java он вдобавок зависит от файловой системы).
- Не перенесены конструкции, которых нет в Train Ticket и которые Java тоже не разбирает осмысленно (`op: unsupported` / `text`): `switch`-выражения, `yield`, локальные классы, `outer.new Inner()`, шаблоны `instanceof`. Если они появятся в другом проекте, IR получит те же маркеры, но тексты `text` могут отличаться от Java печатью.
- Скелет читается своим кодом, а не `archonity-io`: crate автономен и собирается отдельно.
- Java-`archparse` не удалён и не вызывается из `run_final.sh`. Отката на Java при сбое Rust нет: сбой разбора — запись в рамке Р2 (`ATTENTION.txt`), прогон идёт по артефактам, лежащим в папке.
