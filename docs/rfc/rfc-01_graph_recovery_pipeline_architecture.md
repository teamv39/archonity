# RFC-001: Архитектура пайплайна восстановления графа

* **Статус:** superseded (заменен [RFC-05](rfc-05_hybrid_recovery_pipeline_and_arbitration.md))
* **Дата:** 15 октября 2026

> **Примечание:** Данный документ признан устаревшим и полностью поглощен целевым стандартом: **[RFC-05: Гибридный пайплайн реконструкции графа и трехзонный арбитраж](rfc-05_hybrid_recovery_pipeline_and_arbitration.md)**.

---

## TL;DR
Пайплайн восстановления графа состоит из 5 последовательных шагов: детерминированный парсинг Spring (JavaParser) и конфигов в единый `facts.json`; проверка рантайм-достижимости через внутрисервисный Call Graph в NetworkX для отсева мертвого кода; извлечение прямых связей с БД и очередями; ML-достройка неразрешенных связей (CatBoost) и сборка транзитивного замыкания с формированием `evidence.json`.

---

## 1. Общая схема
Пайплайн состоит из 5 последовательных этапов:
1. **Экстракция фактов (AST + Configs):** парсинг исходного кода и конфигураций в промежуточный JSON.
2. **Сборка базового графа:** детерминированное сопоставление точек входа и исходящих вызовов.
3. **Фильтрация (Dead Code Elimination):** удаление вызовов из недостижимого в рантайме кода.
4. **Достройка связей (ML Link Prediction):** предсказание ребер для динамических и неразрешенных вызовов.
5. **Пост-обработка:** транзитивное замыкание, фильтрация по порогу уверенности и экспорт в целевой формат.

---

## 2. Модуль статического анализа кода

### 2.1. Java / Spring (основная кодовая база)
Инструменты: `Spoon` или `JavaParser` (с подключенным Symbol Solver).

* **Точки входа (Inbound):**
  * Поиск классов с `@RestController`, `@Controller`.
  * Извлечение маршрутов из `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`.
  * Конкатенация префикса контроллера и пути метода, сохранение HTTP-метода, сигнатуры входных параметров и типов возвращаемых DTO.
* **Исходящие вызовы (Outbound):**
  * Поиск вызовов `RestTemplate` (`exchange`, `getForObject`, `postForEntity` и др.), `WebClient`, интерфейсов `@FeignClient`.
  * **Протягивание констант (Constant Propagation):** сборка целевого URL внутри метода из строковых литералов, локальных переменных, констант класса и вызовов вспомогательных методов (например, `getServiceUrl(...)`).
  * Приведение собранного URL к нормализованному шаблону (замена динамических подстановок на `{param}`).
* **Брокеры сообщений:**
  * Извлечение точек чтения (`@RabbitListener`, `@KafkaListener`) и записи (`RabbitTemplate`, `KafkaTemplate`) с привязкой к именам очередей, топиков и роутинг-ключей.

### 2.2. Полиглот-сервисы (Go, Python, Node.js)
Инструмент: `tree-sitter` + регулярные выражения.
* Извлечение объявлений HTTP-роутов (Express, Flask/FastAPI, `net/http`, Gin).
* Извлечение исходящих HTTP-запросов и обращений к клиентам БД по строковым шаблонам.

## 3. Модуль анализа конфигураций и БД

Инструменты: `PyYAML`, `javaproperties`.

* **Сетевая топология и роутинг:**
  * Парсинг `application.yml`, `application.properties`, `docker-compose.yml`, конфигов API Gateway / Nginx.
  * Маппинг логических имен сервисов, портов, переменных окружения и префиксов маршрутизации.
* **Базы данных:**
  * Извлечение названия БД/схемы из `spring.datasource.url` и `spring.data.mongodb.uri`.
  * Парсинг аннотаций `@Entity`, `@Table(name = "...")`, `@Document(collection = "...")` и SQL-запросов в `@Query`.
  * Формирование отдельного ребра от каждого микросервиса к соответствующему узлу таблицы/коллекции.

---

## 4. Графовое ядро и алгоритмы фильтрации

Инструмент: `NetworkX`.

* **Резолвинг HTTP-связей:**
  * Сопоставление нормализованных шаблонов исходящих вызовов с реестром входных эндпоинтов по регулярным выражениям и типу HTTP-метода.
* **Отсев мертвого кода (фильтрация под runtime Golden Set):**
  * Построение внутрисервисного графа вызовов методов (`Call Graph`).
  * Проверка достижимости: исходящий вызов внешнего сервиса или БД добавляется в итоговый граф только в том случае, если до вызывающего метода существует путь от публичного контроллера, слушателя очереди или `@Scheduled` задачи.
* **Транзитивное замыкание:**
  * Построение ориентированного графа прямых вызовов.
  * Обход в глубину/ширину (DFS/BFS) для генерации косвенных зависимостей по правилу $A \to B \to C \implies A \to C$ (с учетом правил целевой схемы).

---

## 5. ML-модуль (Link Prediction)

Используется только для пар узлов, где статический анализ не дает однозначного ответа (динамическая генерация URL, общие интерфейсы, восстановление вырезанных ребер скелета).

* **Признаковое описание для пары вершин $(u, v)$:**
  * Косинусная близость эмбеддингов кода методов и сигнатур (`UniXcoder` или `GraphCodeBERT`).
  * Совпадение имен и структуры полей DTO на входе и выходе.
  * Лексическое сходство имен сервисов, методов и URL-сегментов (BM25, Jaccard по токенам `camelCase` / `snake_case`).
  * Топологические признаки из входного скелета графа: входящая/исходящая степень вершин, количество общих соседей, Adamic-Adar индекс.
* **Классификация и калибровка:**
  * Градиентный бустинг (`CatBoost` / `LightGBM`) поверх табличных признаков для предсказания наличия ребра и его типа.
  * Подбор порога вероятности $p_{\text{threshold}}$ на обучающей выборке напрямую под максимизацию метрики IoU. Детерминированные находки из AST получают вес $1.0$.

## 6. Отладка и артефакты для проверки

* **Промежуточный контракт (`facts.json`):**
  * Все парсеры пишут результаты в единый JSON-формат: список узлов сервиса, список входных эндпоинтов, список исходящих вызовов (с флагом достижимости из точки входа), список таблиц БД.
* **Трассировка решений (`evidence.json`):**
  * Для каждого добавленного ребра сохраняется запись: источник (`AST_EXACT`, `CONFIG`, `ML_PREDICTED`), файл и номер строки, вес уверенности.
* **Визуальный дамп графа:**
  * Рендер собранного графа в HTML (`PyVis` / `Cytoscape`) с цветовой разметкой ребер по источникам для ручного поиска аномалий (изолированные сервисы, ложные кластеры).
* **Интеграционный интерфейс (опционально):**
  * Локальный CLI / MCP-скрипт поверх итогового JSON-графа с функциями получения зависимых узлов (`blast_radius`) и кратчайших путей между сервисами.
