## 1. Контекст и проблема

**Цель:** восстановить вырезанные рантайм-связи в предоставленном скелете графа для проекта **Train Ticket** (~40 Spring-сервисов) с максимальным значением метрики **IoU** ($TP / (TP + FP + FN)$).

### Почему чистые подходы проигрывают по отдельности:
1. **Только статический парсер (AST):** даёт почти 100% точность (Precision), но теряет неявные вызовы, склеенные через переменные или интерфейсы (низкий Recall).
2. **Только ML/эвристики:** находят неочевидные связи (высокий Recall), но неизбежно генерят шумные ложные рёбра (падают в $FP$, что фатально для IoU).
3. **End-to-End Fine-Tuning нейросети:** невозможен из-за малого размера датасета (в Train Ticket всего ~200–400 связей — модель переобучится за 2 эпохи) и ограничений по железу (Local-First, без облачных GPU).

**Предлагаемое решение:** разделить сбор данных на два независимых источника (Детерминированный парсер + Движок эвристик и эмбеддингов), свести их в матрицу расхождений и провести количественный арбитраж через легковесный классификатор с точечной валидацией сложной зоны локальной LLM.

---

## 2. Требования и технические ограничения

1. **Strict Local-First:** всё решение исполняется локально. Никаких внешних API (OpenAI, Claude).
2. **Запрет рантайма:** проект не запускается, трассировки логов во время теста запрещены.
3. **Оптимизация под IoU:** любая гипотеза со статусом «может быть» штрафует команду сильнее, чем невключённое спорное ребро. Точность приоритетнее всеядности.
4. **Привязка к скелету:** идентификаторы вершин и типы рёбер должны строго соответствовать `skeleton.json` от организаторов.

## 3. Архитектура репозитория и модулей

```text
├── data/                       # [В .gitignore] Исходники Train Ticket и skeleton.json
├── archparse/                  # Модуль 1: Детерминированный парсер (Java 17/21 + JavaParser)
│   └── src/...                 # Сканирует AST, конфиги YAML, строит внутрисервисный Call Graph
├── engine-python/              # Модуль 2: Движок эвристик и эмбеддингов (Python)
│   ├── embeddings.py           # Получение векторов кода через UniXcoder / CodeBERT
│   └── heuristics.py           # Не-AST эвристики (порты, docker-compose, fuzzy-матчинг имен)
├── arbitrator/                 # Модуль 3: Аналитика и арбитраж (Аналитик)
│   ├── train_ranker.py         # Обучение CatBoost на известных рёбрах скелета
│   ├── threshold_opt.py        # Подбор порога IoU через Optuna
│   └── llm_verifier.py         # Проверка точечной «серой зоны» локальной 7B-моделью
├── graph-builder/              # Модуль 4: Сборщик графа (NetworkX)
│   ├── merge.py                # Вливание предсказанных рёбер в базовый скелет
│   └── closure.py              # Транзитивное замыкание зависимостей
└── run_pipeline.sh             # Скрипт полного прогона всего пайплайна одной кнопкой
```

## 4. Поток данных и JSON-контракты

Пайплайн делится на 4 последовательных шага. Обмен между модулями происходит строго через промежуточные JSON-файлы на диске.

```
   [Train Ticket Source Code] + [skeleton.json]
                 │                    │
        ┌────────┴────────┐           │
        ▼                 ▼           │
 ┌─────────────┐   ┌─────────────┐    │
 │ parser-java │   │engine-python│    │
 └──────┬──────┘   └──────┬──────┘    │
        │                 │           │
   facts.json       candidates.json   │
        │                 │           │
        └────────┬────────┘           │
                 ▼                    │
         ┌───────────────┐            │
         │  arbitrator   │            │
         └───────┬───────┘            │
                 │ resolved_edges.json│
                 ▼                    ▼
         ┌───────────────────────────────┐
         │         graph-builder         │
         └───────────────┬───────────────┘
                         ▼
                 submission.json
```

### Контракт 1: Выход Java-парсера (`facts.json`)
Факты, подтвержденные синтаксическим анализом (Confidence = 1.0) и список неразрешенных вызовов:

```json
{
  "confirmed_edges": [
    {
      "source": "ts-order-service",
      "target": "ts-station-service",
      "type": "CALLS_HTTP",
      "evidence": "RestTemplate: /api/v1/stationservice/stations"
    }
  ],
  "unresolved_calls": [
    {
      "call_id": "call_42",
      "caller_service": "ts-preserve-service",
      "caller_method": "preserveTicket",
      "raw_url_expr": "getServiceUrl(\"ts-order-service\") + \"/order\"",
      "payload_dto_fields": ["userId", "tripId", "seatType"],
      "http_verb": "POST"
    }
  ]
}
```

### Контракт 2: Выход движка эвристик (`candidates.json`)
Python-движок сопоставляет каждый неразрешенный вызов со всеми эндпоинтами и рассчитывает матрицу сходства:

```json
[
  {
    "call_id": "call_42",
    "target_service": "ts-order-service",
    "target_endpoint": "/api/v1/orderservice/order",
    "target_http_verb": "POST",
    "features": {
      "codebert_similarity": 0.84,
      "bm25_name_similarity": 0.61,
      "dto_fields_jaccard": 0.75,
      "http_verb_match": 1,
      "host_or_port_match": 1
    }
  }
]
```

### Контракт 3: Финальный сабмит (`submission.json`)
Формат, полностью совместимый со схемой организаторов:

```json
{
  "nodes": [ ... ],
  "edges": [
    {
      "source": "ts-preserve-service",
      "target": "ts-order-service",
      "type": "CALLS_HTTP",
      "meta": {
        "resolved_by": "CatBoost_Threshold_0.74",
        "confidence": 0.91
      }
    }
  ]
}
```

## 5. Механика арбитража (Зона исследования)

Вместо субъективного отбора пар, следует настроить трёхзонную модель принятия решений:

1. **Зелёная зона ($P \ge 0.85$ или факт из AST):**
    * Связи, подтверждённые статикой или получившие максимальный скор от CatBoost.
    * **Действие:** автоматически включаются в граф.

2. **Красная зона ($P < 0.35$):**
    * Случайные совпадения, маловероятные вызовы, мёртвый код.
    * **Действие:** безусловно отбрасываются (защита от падения IoU).

3. **Серая зона ($0.35 \le P < 0.85$):**
    * Спорные вызовы (обычно это 15–30 краевых случаев на весь проект), где модель не уверена, а статика спасовала.
    * **Действие:**
        * *Базовый вариант:* строгий математический срез по порогу `Optuna` (максимизирующий IoU на локальной валидационной части графа).
        * *Продвинутый вариант:* отправка только этих 15–30 сниппетов в локальную легковесную LLM (`Qwen2.5-Coder-7B`) с бинарным вопросом: *«Вызывает ли метод А сервис Б?»*.

## 6. Преимущества и недостатки подхода

### Плюсы (Почему это взлетит):
* **Устойчивость к сбоям:** если сломается локальная LLM или Python-пайплайн, у команды остаётся `facts.json` от Java-парсера, который сам по себе выдаст стабильный baseline (IoU ~0.65–0.75).
* **Мгновенная отладка:** любое спорное ребро можно отследить по признакам в таблице (`features`) — видно, почему алгоритм принял такое решение.
* **Математическая калибровка:** порог отсечения тюнится целевой оптимизацией под $TP/(TP+FP+FN)$, а не угадывается вручную.
* **Независимая параллельная работа:** джавист углубляет точность AST, питонист пилит фичи из кода, аналитик крутит модели классификации.

### Минусы и риски (О чём надо подумать):
* **Проблема холодного старта валидации:** чтобы обучить CatBoost и подобрать порог Optuna, нужен обучающий граф. Нам придётся искусственно прятать часть известных рёбер из скелета, чтобы проверять качество восстановления.
* **Необходимость единого маппинга ID:** если в Java сервис называется `ts-order`, а в Python `ts-order-service`, соединение упадёт. Нужно сразу зафиксировать нормализатор идентификаторов по `skeleton.json`.
* **Сложность транзитивного замыкания:** при раскрутке связей $A \to B \to C$ одна ложная связь на раннем этапе порождает каскад ошибок. В транзитивное замыкание должны уходить только рёбра с высокой уверенностью.
