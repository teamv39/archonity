## TL;DR
Вместо тяжелой монолитной LLM используется архитектура Compound AI: эмбеддинги кода (`UniXcoder-base` / `Jina Code v2`) для семантики методов, Jaccard-сходство контрактов DTO, лексика BM25 и ориентированная топология графа (HITS, Co-citation/Co-usage без инфраструктурных хабов). Признаки агрегируются в `CatBoostClassifier` с регуляризацией через Feature Dropout (`rsm`, feature masking) и подбором порога отсечки через Optuna под максимизацию IoU. Ребра проходят детерминированный пост-процессинг: типизацию по AST-клиентам, безопасное транзитивное замыкание надежных связей и изоляцию таблиц БД. Локальная LLM (`Qwen2.5-Coder-7B`) привлекается строго точечно (15–30 вызовов) только для сложных динамических строковых выражений.

## 1. Мотивация и постановка вопроса

В проекте Archonity решается задача реконструкции ориентированного типизированного графа runtime-зависимостей микросервисной архитектуры по исходному коду и конфигурациям. Целевая метрика — **IoU (Intersection over Union)**:

$$\text{IoU} = \frac{|E_{\text{pred}} \cap E_{\text{gold}}|}{|E_{\text{pred}} \cup E_{\text{gold}}|} = \frac{TP}{TP + FP + FN}$$

В данном документе под термином **«мультимодальность»** понимается архитектура **Compound AI**: применение ансамбля специализированных компактных моделей и алгоритмов, каждая из которых оптимизирована под конкретный тип данных (AST, конфигурации, сигнатуры методов, топология графа, динамические строковые выражения), вместо использования одной большой монолитной LLM.

### Почему монолитная LLM не подходит как ядро пайплайна

1. **Асимметричный штраф за False Positives в метрике IoU.** Монолитные LLM склонны к галлюцинациям связей на основе общих знаний о предметной области (например, «OrderService обязан вызывать PaymentService»), даже если в конкретном репозитории вызов удален или закомментирован. Каждое лишнее ребро ($FP$) увеличивает знаменатель дроби IoU. В ансамбле вероятность ребра калибруется через градиентный бустинг с прямым поиском порога отсечки под максимум IoU.
2. **Требование к Evidence Log (`evidence.json`).** Каждое добавленное ребро обязано содержать точный путь к файлу, номер строки и детерминированное обоснование. Генеративные модели не способны стабильно воспроизводить номера строк для сотен распределенных вызовов.
3. **Фильтрация мертвого кода (Dead Code Elimination).** В Golden Set входят только связи, достижимые из публичных точек входа (контроллеры, слушатели очередей, cron-задачи). Межпроцедурный анализ достижимости эффективно и детерминированно решается графовыми алгоритмами обхода внутрисервисного Call Graph (NetworkX), а не генерацией текста.
4. **Ограничение Local-First и скорость инференса.** Анализ декартова произведения микросервисов ($40 \times 40 = 1600$ пар) через большую модель занимает десятки минут. Ансамбль малых моделей отрабатывает за 20-40 секунд на локальной машине.

## 2. Архитектура пайплайна: Compound AI

Пайплайн разделен на детерминированное ядро, точечный семантический резолвер, мультимодальное признаковое пространство и калибровочный бустинг.

```mermaid
flowchart TD
    subgraph S1["1. Детерминированное ядро (AST + Configs)"]
        SRC["Исходный код (Java, Go, Python, Node.js)"] --> AST["JavaParser / tree-sitter"]
        CFG["application.yml / docker-compose.yml"] --> CNF["YAML / Properties парсер"]
        AST & CNF --> FACTS["facts.json (Inbound, Outbound, DB, CallGraph)"]
        FACTS --> REACH["NetworkX: фильтрация недостижимого кода"]
        REACH --> DET_EDGES["Детерминированные ребра (AST_EXACT, CONFIG: conf = 1.0)"]
    end

    subgraph S2["2. Точечный резолвинг неоднозначностей"]
        FACTS --> UNRES{"Динамический URL / SpEL / Неоднозначный Feign?"}
        UNRES -- "Да (15-30 фрагментов)" --> LLM["Qwen2.5-Coder-7B (Q4_K_M GGUF)"]
        LLM --> NORM_URL["Нормализованный шаблон URL"]
        UNRES -- "Нет" --> PAIRS["Пул пар-кандидатов (u, v)"]
        NORM_URL --> PAIRS
    end

    subgraph S3["3. Мультимодальное признаковое пространство"]
        PAIRS --> F_LEX["Лексика: BM25 + RapidFuzz по токенам"]
        PAIRS --> F_EMB["Семантика кода: Jina Code v2 / UniXcoder"]
        PAIRS --> F_DTO["Контракты: Jaccard по полям DTO и типам"]
        PAIRS --> F_TOP["Ориентированная топология: HITS, Co-citation, без хабов"]
    end

    subgraph S4["4. Классификация, калибровка и пост-процессинг"]
        F_LEX & F_EMB & F_DTO & F_TOP --> CAT["CatBoostClassifier (rsm, Feature Dropout)"]
        CAT --> PROB["Калиброванные вероятности p(u -> v)"]
        PROB --> OPT["Подбор порога p* под Max(IoU)"]
        OPT --> POST["Детерминированный Post-Processing: типизация + транзитивность"]
        DET_EDGES -- "conf = 1.0, без бустинга" --> POST
        POST --> OUT["submission.json + evidence.json"]
    end
```

- **Быстрый локальный бейзлайн:** `microsoft/unixcoder-base`. Легко запускается через HuggingFace `transformers`, не требует тяжелых зависимостей, стабильно кодирует методы и сигнатуры.

## 5. Текстовое и лексическое сопоставление (Lexical Matching)

Практика анализа микросервисных архитектур показывает, что до 70-80% неразрешенных связей надежно сопоставляются по совпадению имен сервисов, сегментов URL и методов контроллеров без применения нейронных сетей.

### Состав компонентов
1. **Декомпозиция токенов:** преобразование CamelCase и kebab-case в списки лексем с удалением типовых стоп-слов (`get`, `by`, `for`). Пример: `ts-order-service` → `['order', 'service']`, `getTripByTripId` → `['get', 'trip', 'by', 'trip', 'id']` → после дедупликации и фильтрации стоп-слов: `['trip', 'id']`.
2. **BM25 (`rank_bm25`):** вычисление релевантности между токенами исходящего вызова и зарегистрированными точками входа контроллеров.
3. **RapidFuzz (C++ реализация Jaro-Winkler и Token Sort Ratio):** нечеткое сравнение путей URL, устойчивое к вариациям версионирования (`/api/v1/` vs `/api/v2/`) и суффиксам (`-service`, `Controller`). Время вычисления одного сопоставления — менее 0.05 мс.
4. **Сравнение схем DTO:** коэффициент Жаккара по именам полей входных и выходных DTO-классов.

## 6. Графовые признаки и топология (Graph Features vs GNN)

### Анализ применимости GNN (R-GCN, GAT, CompGCN)
Графовые нейросети были рассмотрены для задачи Link Prediction на скелете архитектуры. Однако для графа Train Ticket выявлены следующие ограничения:
- **Размер графа:** всего ~40-50 узлов (микросервисов). Количество обучающих ребер скелета мало ($|E| \approx 100-200$).
- **Риск переобучения:** глубокие графовые свертки (R-GCN, GAT) на графах менее 100 узлов быстро переобучаются под топологию конкретного графа и теряют обобщающую способность.
- **Вычислительный оверхед:** настройка message passing и negative sampling в PyG усложняет отладку и не дает преимуществ по сравнению с табличным бустингом.

### Решение: классические ориентированные топологические эвристики

Скелет графа является ориентированным (`DiGraph`). Стандартные библиотечные реализации `nx.adamic_adar_index` и `nx.jaccard_coefficient` в NetworkX ориентированы исключительно на ненаправленные графы и вызывают ошибку `NetworkXNotImplemented`. Кроме того, сведение графа к ненаправленному искажает причинно-следственную структуру зависимостей микросервисов: вызывающий сервис $u$ и вызываемый сервис $v$ играют принципиально разные архитектурные роли.

#### 1. Изоляция инфраструктурных хабов
В инфраструктуре Spring Cloud присутствуют глобальные служебные сервисы:
* `ts-eureka-service` (Service Discovery)
* `ts-config-service` (Spring Cloud Config)
* `rabbitmq` / message broker
* `zipkin` (Distributed Tracing)

Поскольку к Service Discovery и шине сообщений подключены практически все 40+ микросервисов, эти узлы создают паразитные топологические «короткие замыкания»: любая произвольная пара сервисов $(u, v)$ получает высокий показатель общих соседей через Eureka. 
**Правило:** перед вычислением графовых метрик инфраструктурные узлы временно исключаются из графа скелета.

#### 2. Метрики HITS (Hubs and Authorities) из NetworkX
Алгоритм HITS (`nx.hits(G_directed)`) естественно отражает роли сервисов в микросервисной архитектуре:
* **Authority score ($a(v)$):** авторитетность узла как поставщика данных. Высокий балл имеют сервисы-хранилища и ключевые доменные сервисы (`ts-order-service`, `ts-station-service`), к которым сходятся вызовы от многих клиентов.
* **Hub score ($h(u)$):** склонность узла быть координатором/оркестратором. Высокий балл имеют фасады, API Gateway и агрегирующие сервисы (`ts-preserve-service`, `ts-travel-service`), которые вызывают множество смежных систем.

Для каждой пары кандидатов $(u, v)$ формируются признаки:
* `hits_hub_u`: Hub score вызывающего сервиса $u$.
* `hits_auth_v`: Authority score вызываемого сервиса $v$.
* `hits_product`: $h(u) \times a(v)$ — совместная вероятность взаимодействия оркестратора с авторитетным провайдером.

#### 3. Направленные метрики окрестности (Directed Neighborhoods)
* **Co-citation (общие исходящие цели / shared callees):**
  $$\text{Jaccard}_{\text{succ}}(u, v) = \frac{|\text{Succ}(u) \cap \text{Succ}(v)|}{|\text{Succ}(u) \cup \text{Succ}(v)|}$$
  Отражает функциональное сходство потребителей двух сервисов.
* **Co-usage (общие клиенты / shared callers):**
  $$\text{Jaccard}_{\text{pred}}(u, v) = \frac{|\text{Pred}(u) \cap \text{Pred}(v)|}{|\text{Pred}(u) \cup \text{Pred}(v)|}$$
* **Двухшаговая достижимость (2-hop reachability):**
  Булев флаг и количество промежуточных сервисов $w$ таких, что $u \to w \to v$.
* **Длина кратчайшего ориентированного пути:** расстояние по ориентированному графу от $u$ до $v$ (с флагом `is_unreachable`, если пути нет).

Все метрики вычисляются через `NetworkX` на локальном CPU менее чем за 0.5 секунды.

## 7. Финальный классификатор и максимизация IoU

### Выбор модели: CatBoostClassifier
В качестве итогового классификатора выбран **CatBoost**:
- **Устойчивость к переобучению на малых выборках:** симметричные (обливиусные) деревья обеспечивают сильную регуляризацию.
- **Нативная работа с категориальными признаками:** протоколы вызова, HTTP-глаголы, типы DTO обрабатываются без One-Hot кодирования.
- **Интерпретируемость (Tree SHAP):** CatBoost позволяет извлекать вклад каждого признака в решение, что используется для заполнения поля `details` в `evidence.json`.

### Регуляризация и Feature Dropout

На малых графах (~200–400 ребер) бустинг склонен переобучаться на доминирующие признаки (например, полное совпадение полей DTO или токенов в BM25). В реальном коде у многих вызовов DTO отсутствует (передается `Response<Object>`, сырой JSON или примитивный `Long id`), из-за чего модель, не научившаяся работать без DTO, ошибается.

Для надежности ансамбля применяются две техники регуляризации:
1. **Feature Masking при аугментации данных:** на этапе подготовки обучающих пар с вероятностью $p_{\text{drop}} = 0.2$ признаки DTO и лексики принудительно заменяются на `NaN` / дефолтные значения. Это заставляет деревья обучаться на кодовых эмбеддингах (`UniXcoder`) и топологии (`HITS`, Co-citation).
2. **Random Subspace Method (`rsm` / `colsample_bylevel`):** при обучении CatBoost устанавливается `rsm = 0.75`. На каждом сплите дерево видит только случайную выборку признаков, что исключает монополизацию сплитов одним сильным признаком.

### Калибровка порога под метрику IoU
В отличие от стандартной максимизации ROC-AUC или LogLoss, порог вероятности $p^*$ подбирается прямой одномерной оптимизацией на валидационных фолдах:

$$p^* = \arg\max_{p \in [0.1, 0.9]} \text{IoU}\left( E_{\text{pred}}(p), E_{\text{gold}} \right)$$

Все детерминированные ребра из AST получают фиксированный скор $1.0$. Для предсказанных бустингом ребер добавляются только те, у которых $P(u \to v) \ge p^*$.

### Детерминированный Post-Processing и правила графа (Graph Rules)

После отсечки по порогу $p^*$ принятые ребра проходят обязательный детерминированный этап постобработки:

#### 1. Типизация рёбер (Edge Typing)
Метрика соревнования IoU обнуляет $TP$, если тип ребра или направление указаны неверно. Для каждого ребра тип назначается детерминированно по AST-клиенту вызова:
* `RestTemplate`, `WebClient`, `@FeignClient` $\implies$ `CALLS_HTTP`
* `RabbitTemplate`, `@RabbitListener`, Kafka-клиенты $\implies$ `PRODUCES_MESSAGE` / `CONSUMES_MESSAGE`
* `@Entity`, `@Table`, Spring Data Repositories $\implies$ `READS_DB` / `WRITES_DB`

#### 2. Безопасное транзитивное замыкание (Transitive Closure)
По правилам соревнования граф должен содержать косвенные связи ($A \to B \to C \implies A \to C$).
* **Защита от каскадных False Positives:** транзитивное замыкание выполняется **строго после** отсечки по порогу $p^*$ (или только для Зеленой зоны высокой уверенности). Одно ошибочное ребро с низкой вероятностью при раскрутке графа создает каскад из 5–10 ложных косвенных связей, фатально увеличивая знаменатель IoU ($FP$).

#### 3. Правило изоляции баз данных
* Если несколько микросервисов обращаются к одной таблице БД, формируются независимые ребра от каждого сервиса к узлу таблицы.
* Узлы БД являются терминальными (sinks) и безусловно исключаются из транзитивного замыкания (сервис $A$ не может транзитивно вызывать сервис $B$ через таблицу базы данных).

## 8. Сравнение подходов

| Критерий | Монолитная LLM (7B-14B) | Compound AI Pipeline (Archonity) |
|:---|:---|:---|
| **Время прогона** | 30-60 минут на датасет | **20-40 секунд суммарно** |
| **Потребление памяти** | 8-16 GB VRAM постоянно | **~5-6 GB VRAM пиково** |
| **Калибровка под IoU** | Невозможна (дискретный ответ Да/Нет) | **Прямой подбор порога $p^*$ под максимум IoU** |
| **Evidence Log** | Галлюцинации путей и строк | **100% точные строки для AST, SHAP-объяснения для ML** |
| **Правило БД** | Путает независимые ребра к одной таблице | **Детерминированное выделение узлов таблиц через AST** |
| **Dead Code Elimination** | Ошибается в длинных цепочках вызовов | **Детерминированный граф достижимости в NetworkX** |

## 10. План интеграции и зоны ответственности

```mermaid
flowchart LR
    P1["Паша: facts.json (AST)"] --> P2["Миша: Генерация признаков"]
    P3["Денис: facts.json (Config/Polyglot)"] --> P2
    P2 --> P4["Миша: Обучение CatBoost и тюнинг порога"]
    P4 --> P5["Денис: Сборка графа и evidence.json"]
    P5 --> P6["submission.json"]
```

1. **Этап 1 (Входные факты):** Паша формирует `facts.json` для Java-сервисов (контроллеры, клиенты, вызовы БД). Денис закрывает конфигурации и полиглот-сервисы.
2. **Этап 2 (ML-признаки):** Миша реализует скрипт генерации датасета: UniXcoder косинусное расстояние, BM25/RapidFuzz скоры, топологические метрики из скелета.
3. **Этап 3 (Бустинг и порог):** Миша обучает CatBoost на парах с известной разметкой из бейзлайна/скелета и калибрует порог $p^*$ под метрику IoU.
4. **Этап 4 (Точечный резолвинг):** Для неразрешенных динамических URL подключается Qwen2.5-Coder-7B.
5. **Этап 5 (Финализация):** Денис объединяет детерминированные и ML-ребра, формирует `evidence.json` и проверяет схему перед сабмитом в NSUTS.
