## 2. Входные и выходные данные

* **Вход:**
  1. Исходный код микросервисного проекта.
  2. «Скелет графа» (неполный граф архитектуры с удалёнными ключевыми runtime-рёбрами).
* **Выход:** Полный восстановленный граф в формате JSON (строго по схеме организаторов) со всеми прямыми и косвенными runtime-зависимостями.

## 3. Технические ограничения (Hard Constraints)

1. **Запрет динамического анализа:** Строго запрещено запускать анализируемый проект, собирать runtime-логи или дампы трафика. Разрешён только статический анализ (AST, парсинг конфигов, регулярные выражения, NLP, графовые и кодовые ML-модели). Нарушение — дисквалификация или штраф.
2. **Строгий Local-First:** Запрещено обращаться к внешним закрытым облачным API (OpenAI, Anthropic и др.). Все модели должны работать локально.
3. **Среда исполнения:** Собирать Docker-контейнер для тестирующей системы не нужно — инференс и сборка графа выполняются на локальном железе участников.
4. **Бонус за стек:** Язык разработки любой (Python, Java, C++, Rust). За реализацию на **Rust** начисляется дополнительный балл, но приоритет при ранжировании имеет основная метрика качества графа.

## 4. Метрика и правила построения графа

* **Целевая метрика:** **IoU (Intersection over Union)** между множеством предсказанных рёбер $E_{\text{pred}}$ и эталонным набором $E_{\text{gold}}$ (**Golden Set**):

$$
\text{IoU} = \frac{\lvert E_{\text{pred}} \cap E_{\text{gold}} \rvert}{\lvert E_{\text{pred}} \cup E_{\text{gold}} \rvert} = \frac{TP}{TP + FP + FN}
$$

* **Критерий Golden Set:** В эталон входят только те runtime-связи, которые реально срабатывали при прогоне рабочих сценариев проекта (мёртвый и неиспользуемый код в эталон не входит).
* **Ориентированность и типизация:** Ребро засчитывается в $TP$ только при полном совпадении **пары вершин, направления и типа связи**.
* **Транзитивные зависимости:** Цепочки вызовов необходимо раскручивать полностью. Если $A \to B$ и $B \to C$, то изменение в $C$ аффектит $A$ (необходимо явно учитывать косвенные связи согласно схеме задачи).
* **Правило баз данных:** Если два разных микросервиса $S_1$ и $S_2$ обращаются к одной таблице БД $T$, формируются **два отдельных независимых ребра** ($S_1 \to T$ и $S_2 \to T$), а не одно общее.

## 7. Дополнительные фичи для защиты перед жюри (Killer Features)

3. **Ablation Study в README:** Таблица прироста метрики $\text{IoU}$ по слоям (Baseline $\to$ +Java AST $\to$ +Configs/DB $\to$ +Dead Code Filtering $\to$ +ML Link Prediction).
