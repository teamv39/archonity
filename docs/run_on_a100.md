# Запуск на A100 40 ГБ

Инструкция для финального запуска у организаторов: Linux x86_64, одна A100 40 ГБ. Версии моделей и `llama.cpp` закреплены в [`models/manifest.json`](../models/manifest.json), версии Python-пакетов — в `uv.lock`.

## Одна команда

```bash
uv sync --locked && source .venv/bin/activate      # или: pip install -r requirements.txt (Python 3.11+)
scripts/run_final.sh <файлы сценариев>              # без аргументов — S0–S7
```

`scripts/run_final.sh` делает четыре шага:

1. `scripts/fetch_models.py` докачивает в `models/` недостающие файлы и сверяет sha256 каждого с манифестом. Уже лежащие файлы не перекачиваются. `llama.cpp` качается, если не задан `ARCHONITY_LLAMA_SERVER` и `llama-server` нет в `PATH`.
2. Сборка Rust-движка: `cd rust && cargo build --release --locked`, зависимости с crates.io. Версия Rust закреплена в `rust/rust-toolchain.toml` (1.99.1): нет `cargo` — скрипт ставит её через `rustup` в `~/.cargo`, есть `rustup` — доставляет её. `cargo` из пакетов ОС без `rustup` собирает своей версией. `ENGINE=python` пропускает сборку и гонит весь конвейер на Python.
3. `run_eval.py --engine rust --parse-sources --scenarios <файлы> -o output/submission.json`. Сначала `archonity-parse` (Rust) разбирает исходники и скелет и пересобирает `data/ir/` и `data/entity_ir.json` (около секунды, результат байт в байт как закоммиченный; `PARSE_SOURCES=0` берёт готовые, `ARTIFACTS_DIR` задаёт другую папку артефактов). Java и Gradle не нужны. Перед ним скрипт удаляет выдачу, `m1_report.json`, `ATTENTION.txt` и `resources.json` прошлого прогона в той же папке: если `run_eval.py` упадёт, итог не покажет старые. Выдачи нет — код выхода не 0. M1 (заземление шагов) на Python, ответы LLM из кеша. На первом промахе клиент сам поднимает `llama-server`, ждёт `/health` и гасит сервер при выходе. Пока идут вызовы сервера, после каждого такого шага в stderr строка прогресса: `[m1] S8 шаг 3 из 12: вызовов LLM 4 за 26 с -> GET /api/v1/...; всего 40 вызовов, 4.3 мин`. Прогон из кеша их не печатает. Дальше исполнение шагов (M4), правило Spring Security, проекция на рёбра (M5) и запись `submission.json`, `evidence.json`, `decisions.json` делает бинарник `archonity-exec`.
4. Итог: sha256 выдачи, режим M1 из `m1_report.json`, строка «Время команды» (модели, сборка Rust, прогон, пик памяти и видеопамяти) и последней — рамка из `ATTENTION.txt`, если он есть. Подробности ресурсов — в `resources.json` рядом с выдачей: время этапов, пик RSS дерева процессов, пик видеопамяти по `nvidia-smi`, вызовы и токены LLM (README, «Отчёт, ресурсы, архив»).

Выдача строится всегда, код выхода 0:

- файл сценария не той формы (`engine/scenario.py`): UTF-8 с BOM и UTF-16 читаются, нет `id` — имя файла, нет `action` у шага — пустой текст, `n` строкой — целое, шагов нет — пустой блок без сбоя. `--scenarios` принимает и каталог (его `*.json`); путь, по которому ничего не нашлось, — сбой в рамке;
- исключение на шаге — шаг без рёбер, остальные шаги идут дальше; исключение в сценарии — пустой блок `{"edges": []}`;
- Rust не собрался или `archonity-exec` упал — тот же прогон на Python-исполнителе: выдача та же байт в байт, в рамке сбой «движок Rust (откат на Python)». Не собрался Rust — `run_final.sh` удаляет старые бинарники и не пересобирает IR, берутся готовые `data/ir/` и `data/entity_ir.json`;
- конвейер не собрался — повтор без LLM и эмбеддера, не собрался и так — `submission.json` с пустыми блоками всех сценариев;
- LLM не ответила — шаг берёт первый кандидат поиска (режим M1 `partial` или `emergency`);
- эмбеддер не загрузился или отказал (нет `torch`, не хватило видеопамяти, в том числе рядом с сервером `prestart`) — у шагов с новым текстом поиск кандидатов только BM25. Режим M1 при этом `full`, поэтому в рамку идёт отдельная строка: число векторов без модели и причина (`embedding_misses`, `embedding_failure` в `m1_report.json`).

Если хоть что-то из этого случилось, рядом с выдачей появляется `ATTENTION.txt`: что сломалось, на каких шагах, контакт команды. Тот же текст в рамке — последние строки stdout и stderr; список сбоев ещё в `m1_report.json`, поле `failures`. Чистый прогон `ATTENTION.txt` не оставляет. Путь выдачи меняет переменная `OUT`, интерпретатор — `PYTHON`.

Пакет организаторов (скелет, исходники Train Ticket, сценарии) ожидается в `hackaton/tt-challenge/`. Другие пути задаются флагами `run_eval.py`: `--skeleton`, `--targets`, `--scenarios`.

## Требования

- Linux x86_64, NVIDIA A100 40 ГБ, драйвер 570+ (CUDA 12.8).
- Python 3.11+ (кеши и рекорд построены на 3.13) или [`uv`](https://docs.astral.sh/uv/): он сам поставит нужный Python.
- Около 27 ГБ на диске под `models/` и доступ к Hugging Face и GitHub на время `fetch_models.py`.
- Rust 1.99.1 (`rust/rust-toolchain.toml`): ставится скриптом через `rustup`, нужен доступ к crates.io, static.rust-lang.org и sh.rustup.rs. Сборка около минуты (tree-sitter компилирует небольшой C-код грамматики: нужен `cc`/`gcc`).
- Прогону S0–S7 из кеша видеокарта и модели не нужны.

## llama.cpp

- По умолчанию берётся релизная сборка манифеста: `fetch_models.py --llama-cpp` распаковывает её в `models/llama.cpp`, и клиент находит её сам.
- Свой бинарник: `export ARCHONITY_LLAMA_SERVER=<путь>/llama-server`.
- Docker-образа ровно этой сборки нет: `ghcr.io/ggml-org/llama.cpp:server-cuda-*` собираются по ночам из других коммитов.
- Для A100 (sm80) в релизной сборке есть только PTX. Ядра CUDA компилирует драйвер при первом запуске, поэтому первые запросы идут дольше. Без этого шага — сборка из исходников того же коммита:

  ```bash
  git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp && git checkout ba3c05f71da85cd0439e84ba42b0478b24d5db16
  cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=80 && cmake --build build -j --target llama-server
  export ARCHONITY_LLAMA_SERVER=$PWD/build/bin/llama-server
  ```

## Что из кеша, что заново

- S0–S7 целиком из кеша (`cache/llm/`, `cache/emb/`). Сервер не поднимается, выдача совпадает с рекордом байт в байт.
- На новом сценарии из кеша берутся профиль проекта (ответ LLM) и векторы обработчиков.
- Заново считаются векторы шагов нового сценария (эмбеддер) и ответы LLM на его шаги. Новые векторы дописываются в `cache/emb/`, новые ответы — в `cache/llm/`, повторный прогон идёт из кеша.
- Векторы шагов всех сценариев прогона считаются одной пачкой до первого ответа LLM по ним: эмбеддер грузится один раз и сразу выгружается. На A100 сервер LLM тем временем уже грузится (раздел «Память»).
- Голосование выбора останавливается, как только исход ясен: на шаг с единогласными голосами уходит 3 вызова вместо 6, ответ тот же.
- Лог сервера — `output/llama-server.log`.

## Память и параметры сервера

- LLM около 20 ГБ (веса 17.7 ГБ, KV `q8_0` на 32k токенов), эмбеддер около 8 ГБ (bf16). Для A100 это оценка, замеры есть только с видеокарты 16 ГБ.
- Эмбеддер живёт в памяти только пока считает. Порядок в прогоне:
  1. `run_all` вызывает `StepGrounder.prepare`: векторы шагов всех сценариев одной пачкой. Что есть в `cache/emb/`, берётся оттуда; на промахе эмбеддер грузится, считает пачку, дописывает векторы в `cache/emb/`.
  2. После каждой порции промахов эмбеддер выгружает модель (`STEmbedder.release`: `gc`, `torch.cuda.empty_cache()`). Векторы остаются в памяти процесса, повторно модель не нужна.
  3. Ответы LLM идут из кеша; на первом промахе клиент поднимает `llama-server` и ждёт `/health`.
- Запуск сервера заранее (`LLMClient.prestart`). Если у шагов новые тексты (промах кеша векторов), то промахи будут и в кеше LLM. Тогда в п. 1 сервер стартует до загрузки эмбеддера, обе модели грузятся одновременно, и в п. 3 остаётся дождаться `/health`. Выигрыш — время загрузки эмбеддера: на 16 ГБ с холодного диска 155 с, на A100 не замерено. Это делается только когда обе модели помещаются вместе. При `ARCHONITY_LLM_PRESTART=auto` (умолчание) свободной видеопамяти GPU 0 по `nvidia-smi` должно быть не меньше суммы файлов обеих моделей плюс 5 ГиБ запаса — около 29.7 тыс. МиБ. На A100 40 ГБ это выполняется, на 16 ГБ нет: там сервер, как и раньше, поднимается на первом промахе, после выгрузки эмбеддера. Если сервер, запущенный заранее, не поднялся, на первом промахе он запускается ещё раз обычным путём.
- Если промахнулись и векторы обработчиков (другой проект, считаются при сборке M1), и векторы шагов, модель загружается дважды: каждая порция выгружается сразу, чтобы профиль проекта (ответ LLM при сборке M1) не встретился с эмбеддером в памяти.
- После выгрузки в процессе остаётся то, что выгрузить нельзя: библиотеки torch (около 2.2 ГБ ОЗУ на CPU, около 3.7 ГБ с CUDA) и контекст CUDA (около 0.3 ГБ видеопамяти).
- Сбой эмбеддера (нет модели, не хватило памяти) прогон не роняет: dense выключается, поиск идёт по одному BM25 (`m1_report.json`, поле `embedding_misses`).
- Сервер по умолчанию: `--fit off -ngl 999 -fa 1 -ctk q8_0 -ctv q8_0 -c 32768` — все слои на GPU, без `-ncmoe`. Вручную тот же сервер запускает `scripts/start_llm.sh`.
- Уже запущенный сервер на `ARCHONITY_LLM_URL` клиент использует как есть.

| Переменная | Что делает |
|---|---|
| `ARCHONITY_LLAMA_SERVER` | путь к `llama-server` или к единому `llama`; `off` — без автозапуска |
| `ARCHONITY_LLAMA_ARGS` | аргументы сервера после умолчаний, перекрывают их |
| `ARCHONITY_LLAMA_START_TIMEOUT` | сколько ждать `/health`, с (по умолчанию 1800, отсчёт от запуска сервера) |
| `ARCHONITY_LLM_PRESTART` | сервер до эмбеддера: `auto` (по умолчанию, если хватает видеопамяти), `on`, `off` |
| `ARCHONITY_LLM_URL` | адрес сервера, по умолчанию `http://127.0.0.1:8080`; автозапуск — только для loopback |
| `ARCHONITY_EMBED_DEVICE` | устройство эмбеддера: `cuda` или `cpu`; по умолчанию GPU, если он есть |

## Видеокарта меньше 40 ГБ

На 16 ГБ LLM и эмбеддер вместе не помещаются, но вместе они и не работают: эмбеддер выгружается до первого вызова LLM. Нужен один параметр — часть экспертов MoE в RAM:

```bash
export ARCHONITY_LLAMA_ARGS="-ncmoe 7"
```

Замер 21.10 на RTX 5070 Ti 16 ГБ, S0 с пустым кешем LLM: прогон 340 с, из них загрузка модели с диска 284 с, пик видеопамяти 15.4 ГБ, IoU S0 = 1.0.

Сервер вручную — `scripts/start_llm.sh`. Уже скачанную модель кладёт в `models/` команда `python scripts/fetch_models.py --from <путь>/Qwen3.6-35B-A3B-UD-IQ4_XS.gguf`: она проверяет sha256 и ставит жёсткую ссылку или копию.
