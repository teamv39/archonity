# Тестирующая система: что о ней известно

Обновлено 19.10.2026, после итога **1.00000** (посылки 27 и 28). Документ сводит в одно место правила платформы NSUTS, правила эталона и способы мерить по платформе. Подробности отдельных правил — в [annotation_rules.md](annotation_rules.md), полная таблица посылок — в [roadmap.md](roadmap.md).

Откуда известно:

- **[орг]** — README, REFERENCE и `context/README.md` пакета организаторов (`hackaton/tt-challenge/`);
- **[S0]** — открытый эталон `gold/S0.json`;
- **[посылка N]** — проверено отправкой на платформу.

## 1. Платформа

| Правило | Откуда |
|---|---|
| Ответ — один JSON: `project` и `scenarios`, у сценария список `edges` из `source`, `relation`, `target`. Концы — ID методов и таблиц из `nodes` скелета дословно, плюс служебный `scenario:Sx` | [орг] |
| Сдача — zip: `submission.json` в корне, код решения рядом. Собирать `pack_submission.py` (LF, POSIX-права); архив с вложенной папкой или JSON без архива дают статус W и балл 0 | [орг], опыт 17.10 ([skill сборки](../skills/build-submission/SKILL.md)) |
| Для каждого сценария и вида рёбер — IoU `|P ∩ G| / |P ∪ G|`. Оба множества пусты — 1; эталон пуст, а в ответе есть ребро — 0 | [орг] |
| Балл сценария — среднее по `executes`, `calls`, `remote`, `data`; итог — среднее по S1–S7. S0 в итог не входит, нет блока сценария — 0 за него | [орг] |
| Сдавать можно сколько угодно, лимита нет; в зачёт идёт последняя принятая сдача целиком | [орг], посылки 0–28 за 16–19.10 |
| Таблица результата: баллы S1–S7 с 3 знаками и итог с 6 знаками, но шестой знак всегда 0 — **реальная точность итога 1e-5** | посылки 20–28 |
| Код лучших решений организаторы перезапускают: только статический анализ, без запуска Train Ticket и рантайм-данных; ответ должен получаться сданным кодом | [орг] |
| Решения на Rust получают ×1.10 (не выше 1.0) после проверки кода. Мы на Python, надбавку не берём | [орг] |
| Локально `platform/evaluate_golden.py` считает балл только по S0, у S1–S7 проверяет формат: ID, отношения, виды вершин | [орг] |

## 2. Эталон

Эталон получен прогоном Train Ticket с записью исполнения: «runs with the second trip … gave the same methods, calls, remote calls and data accesses (only statements differed, by 1 line)» [орг, `context/README.md`]. Ниже — что про него известно, по темам.

### Шаги

| Правило | Откуда |
|---|---|
| Один шаг — один запрос через шлюз. Ответ — множество на весь сценарий, порядок и повторы не важны | [орг] |
| Шаг, которого нет в UI (цена заказа, запись страховки, расчёт возврата), шлёт запрос: обработчик выбирается по коду сервиса | уникальные рёбра таких шагов в S1, S4, S5, S7 при балле 1.000 |
| Запросы, которые UI шлёт сам при открытии страницы, отдельным шагом не считаются: `getAllFood` при открытии бронирования в S3 не исполняется | посылка 19 |
| «Refresh the list of orders» без типа поезда — один запрос, по типу поезда заказа | [S0], посылка 1 |
| Если обработчик Spring вызвать не может (`@PathVariable` не совпадает с шаблоном пути), шаг идёт через рабочий обработчик того же контроллера с тем же входом: «Browse the food stores at Suzhou station» → `POST /stationfoodstores`, а не `GET /stationfoodstores/{stationId}` | посылки 13–14, 21–27, [разбор](researches/reaching_1_0.md) |
| Неудачный шаг: код до отказа учитывается | [орг] |
| «Первый» рейс, контакт, магазин — первый в ответе системы; другой выбор исполнения не меняет | [орг] |

### Методы и вызовы

| Правило | Откуда |
|---|---|
| Только методы проекта. Lombok-методы, методы библиотек, геттеры и конструкторы, вызванные библиотекой через отражение, не входят | [орг], [S0] |
| Метод проекта, который вызвала библиотека, — `executes` без `calls`: контроллеры (DispatcherServlet), `JWTFilter#doFilterInternal`, методы `UserDetails`, `equals` из `List.contains` | [орг], [S0], посылка 1 (R5) |
| Lombok-`toString` при логировании через `{}` (уровень INFO) вызывает рукописные геттеры: `TravelResult#isStatus()` — `executes` во всех сценариях, без `calls` | посылки 11–12 (R5) |
| Ребро `A → M` ставится и тогда, когда `M` вызвала библиотека, если ближайший проектный кадр — `A` и у `A` есть call_site с именем `M` | [S0] (R6) |
| Конструктор — в ответе, только если из него исполнился вызов метода проекта; рёбер `calls` в конструктор нет. Способ создания не важен: `new`, Hibernate, Jackson (`RebookInfo()` → `Date2String`) | посылки 9, 10, 17 (R7, [ADR-006](adr/adr-006_constructor_visibility.md)) |
| Сеттеры, которые зовёт Jackson, не учитываются | [S0] (R8) |
| Методы enum, в том числе через константу (`OrderStatus.PAID.getCode()`), учитываются | [S0], посылка 18 |
| Вызов через интерфейс — ребро к исполнившейся реализации | [орг] (R2) |

### Межсервисные вызовы и данные

| Правило | Откуда |
|---|---|
| `remote` — отправитель → обработчик другого сервиса, HTTP и RabbitMQ; доставка RabbitMQ учитывается | [орг], посылка 2 (R13) |
| `SecurityServiceImpl#check` опрашивает оба сервиса заказов во всех сценариях | зонд `--security-check-scope`, 19.10 |
| `data` — от метода, где стоит вызов репозитория, к каждой таблице, куда ушёл SQL; отложенный SQL ORM — к тому же методу | [орг] |
| Все `data`-рёбра эталона есть среди пар `data_access` скелета | [орг] |
| Таблица коллекции сущности — отдельная вершина и отдельное ребро, только если коллекцию загрузили | [орг], платформа 17.10 (R10, +0.015) |
| Зондирующий SELECT к `orders` в S2 есть | посылка 4 |

## 3. Как мерить по платформе

Цена одного ребра: `executes` или `calls` — около 0.0002 итога, `remote` или `data` — около 0.001.

| Способ | Что даёт | Инструмент |
|---|---|---|
| Сравнить выдачу с рекордом до посылки | что посылка вообще проверяет | `scripts/compare_submissions.py` |
| Убрать вид рёбер во всех сценариях и добавить k заведомо лишних | FP и FN по видам с погрешностью ±5 рёбер | `scripts/probe_kind_counts.py` |
| Убрать вид рёбер в одном сценарии | IoU ячейки = 28 × (итог базы − итог зонда), погрешность ±2.8e-4: для `data` (P ≈ 30) — точные FP и FN, для `executes`/`calls` — 2–3 кандидата, спорное снимает совместная проверка суммы | `scripts/probe_cells.py` |
| Добавить или убрать класс рёбер под флагом | подтверждение механизма | флаги `RuntimeRules`, `scripts/probe_edge_classes.py` |

Правила работы с платформой:

- одна посылка отвечает на один вопрос;
- зонды — по видам, ячейкам и классам рёбер, а не по отдельным рёбрам; ручная правка `submission.json` — замер, а не решение;
- правило, которое держится только на прочтении текста организаторов, — гипотеза, её проверяют посылкой первой;
- форма нехватки называет механизм: «2 метода, 1 вызов, 2 таблицы, без `remote`» — пропущенный вход шага, а не ветка внутри сервиса;
- последней на платформе должна стоять выдача кода.

Посылки 11–19 — зонды Дениса ([how_we_achieved_0_99457.md](how_we_achieved_0_99457.md)), 20–28 — перенос в код и замер.

Что вошло в код (флаги `run_eval.py`, все включены по умолчанию):

- R7: `--jackson-ctor` — рукописный конструктор тела запроса исполняется на входе шага и в межсервисном вызове, отбор — проекция ADR-006;
- R5: `--lombok-tostring` — аргументы `info`/`warn`/`error` с `{}` обходятся как Lombok-`toString`;
- R20: `--unbound-handlers` — обработчик с несвязываемым `@PathVariable` заменяется рабочим того же контроллера (`engine/grounding/binding.py`).

Обобщения 19.10 выдачу не меняют, только убирают имена Train Ticket из правил ([аудит, раздел 6](researches/universality_audit_after_1_0.md)): `--spring-security semantic` (Spring Security по контракту фреймворка), `--m4-m3-refs off` (M4 без модели M3), `--module-roles skeleton` (общий модуль по `depends_on`, близнецы по совпадению API). Старые режимы — `names`, `on`, `names`.

`python run_eval.py` без ключей даёт рекорд 1.0 байт в байт (sha256 в [eval/records/](../eval/records/README.md)). Подробно: [code_record_drift.md](researches/code_record_drift.md) — как код догнал 0.99457, [reaching_1_0.md](researches/reaching_1_0.md) — как дошли до 1.0.

По дороге одно правило пришлось заменить. R20 «шаг — действие формы без запроса» сошёлся с посылкой 20, но объяснял её неверно и прятал 5 рёбер в каждом из S2 и S3. Замер ячеек это показал.

## 5. Чего мы не знаем

- **Как организаторы выбирали запрос шага.** Факты: шаги без UI шлют запрос по коду сервиса, запросы при открытии страницы не считаются, сломанный обработчик заменён рабочим. Похоже на сценарий, написанный вручную по API, а не на воспроизведение UI. Это вывод по трём наблюдениям, а не правило организаторов.
- **Будут ли при проверке кода другие сценарии.** README: «решение одно — программа, которая по тексту любого сценария строит его блок». Правила по именам методов и сценариев — риск; их аудит — в плане на 21.10 ([universality_audit_19_10.md](researches/universality_audit_19_10.md)).
- **Точный инструмент записи эталона.** Видимость конструкторов (R7) объясняется гипотезой «агент перехватывает методы, но не конструкторы» ([constructor_project_calls_rule.md](researches/constructor_project_calls_rule.md)).
