## Архитектурный пайплайн решения (идейка)

### Цель:
Восстановить отсутствующие runtime-связи в предоставленном **скелете графа** для микросервисов **Train Ticket** и выбить максимальный **IoU** без ложных срабатываний.

---

### Входные данные:
1. Исходный код проекта `Train Ticket` (~40+ Spring Boot сервисов).
2. `skeleton.json` — неполный граф архитектуры от организаторов.

---

### 1. Слой статического анализа и фактов (Java / CLI-утилита)
> **Инструменты:** Java 21, `JavaParser`, `jackson-dataformat-yaml`.

* **Чтение конфигов:** парсим `application.yml` каждого сервиса (вытаскиваем порты, имена баз данных MySQL/Mongo).
* **Поиск отправных точек:** фиксируем все публичные точки входа (`@RestController`, `@Scheduled`, `@RabbitListener`).
* **Внутрисервисный Call Graph (отсев мертвого кода):** строим граф вызовов внутри сервиса от отправных точек. Вызовы из методов, недостижимых от контроллеров, **выбрасываются**.
* **Склейка строк (Constant Folding):** восстанавливаем URL в `restTemplate` из строковых констант, путей классов и аннотаций (они могут быть написанны как попало).
* **Маппинг БД:** связываем сервисы с таблицами через `@Table`, `@Entity`, `@Document` (отдельное ребро на сервис, как требует регламент).

**Результат на выходе (два JSON-файла):**
1. `confirmed_edges.json` — 100% сошедшиеся вызовы и связи с БД (вероятность 1.0, без ML).
2. `unresolved_calls.json` — спорные вызовы (с динамическими URL). Внутрь объекта Java сразу пакует контекст: имя вызывающего метода, сниппет кода и поля DTO. *Python по файлам проекта не ищет.*

---

### 2. Слой извлечения признаков (Feature Extraction)
> **Инструменты:** Python, `transformers` (`microsoft/unixcoder-base` или `CodeBERT`), `rank_bm25`.

Берём каждый неразрешённый вызов и сопоставляем его со списком потенциальных эндпоинтов-серверов. Для каждой пары параллельно считаем фичи:
* **CodeBERT score:** косинусное расстояние между эмбеддингами кода клиента и сервера (семантика).
* **BM25 score:** пересечение токенов в именах методов и URL (лексика).
* **DTO overlap:** процент совпадающих полей в моделях запроса/ответа.
* **Metadata match:** совпадение HTTP-глагола (GET/POST/PUT), совпадение портов/хостов.

**Результат на выходе:** таблица признаков (DataFrame) для всех пар-кандидатов.

---

### 3. Слой арбитража и порога
> **Инструменты:** `CatBoostClassifier`, `Optuna`, `Scikit-learn`.

* На известных рёбрах из `skeleton.json` обучаем легковесный **CatBoost**.
* Модель выдаёт вероятность наличия связи $P(\text{edge}) \in [0, 1]$ для каждого кандидата.
* **Подбор порога (Optuna):** прогоняем валидацию и находим математически оптимальный порог (например, $P > 0.73$), максимизирующий именно формулу **IoU** ($TP / (TP + FP + FN)$).
* Отсекаем всё, что ниже порога.

**Результат на выходе:** `predicted_edges.json`.

---

### 4. Сборка графа и экспорт
> **Инструменты:** `NetworkX`, `Pydantic`.

* Объединяем `confirmed_edges` + отфильтрованные `predicted_edges`.
* Вливаем найденные рёбра в базовый `skeleton.json`.
* **Транзитивное замыкание:** раскручиваем цепочки зависимостей $A \to B \to C \implies A \to C$ алгоритмами на графах.
* Валидируем финальный JSON по схеме организаторов $\to$ получаем `submission.json`.

---

### Киллер-фичи:
1. **Explainability Log:** для каждого ребра сохраняем причину проведения (`[Rule: RestTemplate_Constant_Match]` или `[ML: CatBoost_Score_0.89]`). Это подтвердит, что результат не был нарандомизирован.
2. **Локальный MCP-сервер:** оборачиваем граф в MCP с тулами `get_blast_radius()` и `get_dependencies()`.
