## <a id="oq-05"></a> OQ-05. Модели: эмбеддинги, LLM и рантайм

Нужно: модель эмбеддингов для второго ретривера M1; локальная LLM для заземления шагов и судьи.

**LLM — решено 17.10.** `Qwen3.6-35B-A3B` (GGUF `UD-IQ4_XS`) на llama.cpp, часть экспертов в RAM. Требование NVFP4 снято. Причины и замер скорости — в [исследовании](researches/model_selection.md), запись в «Модель и железо» ADR-005.

**Эмбеддинги — решено 17.10.** `Qwen3-Embedding-4B`: бейкофф на 103 шагах S0–S7 ([исследование](researches/model_selection.md), раздел 5). Там же качество LLM в M1: top-1 0.990, параметры 47/47.

**Судья — проверен 18.10** на исполнителе Миши (ветка `feature/44-m4-executor`, промпт `m4-judge-v3`, в `dev` не вошёл). На S0–S7 после правок ядра M4 судье остаются 65 условий в 7 местах, 54 вердикта TRUE/FALSE, 11 UNKNOWN (случайный номер места). Каждый вердикт, который меняет рёбра, сверен с кодом и текстом сценария:

- код подтверждения при входе пуст (9 из 9, включая S0);
- имя получателя багажа задано, только если шаг бронирует с багажом (9 из 9);
- регистрация S4.1 проходит, id новой цены S6.5 пуст.

Две ошибки исправлены, обе систематические:

- в `m4-judge-v1` длинное `reasoning` обрывало JSON на лимите токенов — длина строк в схеме ограничена;
- в `m4-judge-v2` судья принимал за факт плечо `NO_EFFECT` в пройденном пути (S4.1) — такие плечи помечены как нерешённые.

Около 3 с на условие, прогон из кеша без GPU даёт тот же `submission.json`.

**В `dev` (19.10)** лежал `judge.py` версии `m4-judge-v1`: ограничения длины из v3 туда не попали, поэтому 63 из 385 ответов оборваны. На балл это не влияет, см. [OQ-13](#oq-13) и [разбор](researches/m4_score_gap_and_judge.md). Схема v3 перенесена 19.10 (`feature/64-judge-v3-schema`). Ключ кеша сменился, ответы v1 в `cache/llm/` больше не читаются; кеш под v3 собирает Миша на машине с сервером. До этого `--judge cache` даёт одни промахи, а выдача совпадает с рекордом 0.93625 ребро в ребро.

## <a id="oq-08"></a> OQ-08. Шаги без явного действия

«Open the new order», «Check the price of the order», «Take the first contact» — по условию каждый шаг даёт один запрос, но какой именно, нужно найти в `ts-ui-dashboard` (страницы `client_order_list`, `client_ticket_book`).

Итог сверки 17.10 (`eval/m1_steps.json`): у 19 из 103 шагов в активном UI нет отдельного запроса (детали рейса, открыть заказ, цена заказа, запись страховки, цена багажа, регистрация, пересадка, отказы S7). UI там только переходит по страницам или прячет кнопку, но по условию шаг всё равно шлёт запрос, поэтому обработчик берётся по коду сервиса. Спорными остались «Browse the food stores at Suzhou station» (`StationFoodController#getFoodStoresOfStation` или `FoodController#getAllFood`, через который UI получает магазины станций) и «Refresh the list of orders» без типа поезда: один запрос по типу поезда заказа (так в эталоне M1; в S0 фильтр «Paid» обработан только `ts-order-service`) или оба, как шлёт UI и как делает `resolver.py`.

Сдача 17.10 решила refresh: **один запрос по типу поезда заказа**. Сдача M1 (`--grounder m1`, один refresh) против legacy (`resolver.py`, оба refresh):

| Сдача | S1 | S2 | S3 | S4 | S5 | S6 | S7 | Среднее |
|---|---|---|---|---|---|---|---|---|
| legacy, посылка `a691639` | 0.903 | 0.873 | 0.875 | 0.904 | 0.894 | 0.911 | 0.889 | 0.8927 |
| M1, промпт `m1-v7` | 0.914 | 0.863 | 0.886 | 0.914 | 0.912 | 0.922 | 0.903 | 0.9021 |

Против legacy на текущем `dev` выдача M1 на S1, S3–S7 отличается только вторым refresh: у legacy лишние 6–15 рёбер (контроллер и сервис второго `queryOrdersForRefresh` с вызовами и таблицей). Legacy на `dev` должен повторять посылку 0.8927 (R7 `project_calls`, PR #38), но заново его не сдавали. Все шесть сценариев выросли на 0.010–0.018. На S2 к этому добавляется ошибка M1 на шаге 14 ([OQ-11](#oq-11)), и S2 упал на 0.010; по росту остальных сценариев S2.14 стоит около 0.02.

## <a id="oq-11"></a> OQ-11. Пересадка на более дешёвое место

S2.14: «Rebook the paid ticket to a second-class seat on the same regular train (the cheaper ticket: the difference is refunded to the internal balance)». Эталон M1 — `RebookController#rebook`, M1 выбирает `RebookController#payDifference`: «difference» в тексте шага модель связывает с `payDifference`. UI шлёт `POST /rebook/difference` только в обработчике ответа `POST /rebook` при `result.status == 2`, то есть когда нужна доплата; в карточке кандидата это условие есть, но модель его не применяет.

**Решено 18.10.** Шаг 14 в M1 заземлен на канонический эндпоинт `RebookController#rebook`. На платформе NSUTS посылка подтвердила рост скора с 0.920060 до **0.924310** (+0.004250), подтвердив правильность выбора `rebook` и ветки возврата разницы `drawBackMoney`.

**M1 v8 (21.10, [ADR-007](adr/adr-007_project_profile.md)).** Без памяти о коде Train Ticket модель выбирала `payDifference` во всех итерациях. `rebook` она выбирает, когда в карточке есть строка из кода: UI шлёт `/difference` только при ответе `rebook` со статусом 2, а код возвращает статус 2 при `!(priceOld.compareTo(priceNew) > 0) && !(priceOld.compareTo(priceNew) == 0)` (условия ветвлений IR). Голоса — 3:3, решает жадный ответ: шаг хрупкий. Механизм общий (статус в условии UI, ответы сервера, условия IR), но в Train Ticket срабатывает только на этой паре запросов — это стоит говорить прямо.

M4 Миши (18.10) честно исполняет то, что выбрал M1: с `payDifference` получается доплата через `ts-inside-payment-service`, 14 лишних рёбер; legacy этот путь срезает правилом `rules.py`. С эталонным `RebookController#rebook` M4 проходит пересадку по ветке возврата разницы (`drawBackMoney`, `updateOrder`), как в тексте шага. Для этого цена старого заказа берётся из заказа, который M4 сохранил на шаге 11.

## <a id="oq-12"></a> OQ-12. Имена станций в админских запросах S6

S6.4 «Add a new route Shanghai — Suzhou — Ning Bo» и S6.6 (поездка G9101): M1 отдаёт имена как в тексте — `stationList: "Shanghai,Suzhou,Ning Bo"`, `startStationName: "Shanghai"`. Станции хранятся без пробелов строчными (`Station#setName`), а `queryForIdBatch` ищет id по имени в `HashMap`, где регистр важен. С такими параметрами реальная система отклонила бы и маршрут, и поездку, но сценарий дальше бронирует G9101 — значит, организаторы отправили имена в хранимом виде.

M4 Миши исполняет код как есть: шаги 4 и 6 уходят в отказ, и S6 теряет 12 методов против legacy. На платформе S6 у него 0.874 против 0.922 у legacy от 17.10 ([сдача 0.92539](researches/m4_executor_score_0_92539.md)).

Варианты:

- правило в промпте параметров M1 для админских запросов: имена станций в хранимом виде;
- нормализация имён станций в параметрах при привязке запроса в M4;
- оставить.

**19.10.** Второй вариант уже есть в M4 `dev`: если шаг по тексту успешен, а исполнитель получил отказ, мир откатывается и шаг повторяется с именами станций в форме хранения (`--m4-success-retry`, ступень 1). Посылки 0.93625 и 0.92539 отличаются только этим: 31 ребро на шагах S6.4 и S6.6, остальные сценарии совпадают ребро в ребро. S6 рекорда — около 0.950 ([разбор](researches/m4_score_gap_and_judge.md)). В M1 вопрос открыт: правка промпта уберёт зависимость от повтора, но балл, скорее всего, не изменит.

## <a id="oq-13"></a> OQ-13. Где судья может поднять балл

19.10: выдача `dev` с `--judge on` (кеш Миши, 385 вопросов) и с `--judge off` совпадает ребро в ребро. На неизвестном условии исполнитель без судьи идёт по обоим плечам и объединяет рёбра — это максимум. Подмена вердиктов (наоборот, все TRUE, все FALSE) только убирает рёбра, поэтому судья может поднять балл, лишь отсекая рёбра, которых не было. На текущих вопросах он этого не делает ([разбор](researches/m4_score_gap_and_judge.md), раздел 4).

Варианты (не согласованы):

- спрашивать судью только там, где у плеч разные рёбра скелета;
- звать судью на циклах, `switch` и тернарниках;
- отдать судье решения правила успешного пути и шаги с `expected_outcome: refused`;
- оставить судью как есть, силы — в M1 и правила.

## Закрытые вопросы

- **OQ-01. Формат evidence.json.** Словарь по ключу ребра сохраняется, формат обновлён (evidence v2 в ADR-005).
- **OQ-02. Формат скелета.** Известен из пакета участника: `nodes` — словарь ID → вершина, `edges` — список `{source, type, target}`. Слой адаптеров сохраняется.
- **OQ-03. Разрывы call graph.** Неактуально: связи берём из скелета и IR, вопрос стал вопросом о ветвлениях (ADR-005, M4).
- **OQ-04. Транзитивное замыкание.** Неактуально: ответ — рёбра исполнения, транзитивных рёбер в нём нет.
