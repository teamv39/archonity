# Аудит модуля archparse и потенциальные оптимизации

**Дата:** 19.10.2026  
**Статус:** Действует  
**Связано:** [roadmap.md](../roadmap.md), [ADR-005](../adr/adr-005_scenario_execution_pipeline.md), [archparse/README.md](../../archparse/README.md)

Документ фиксирует результаты аудита времени, архитектурных проблем (code smells) и план оптимизации Java-модуля `archparse` перед финализацией кодовой базы.

---

## 1. Роль модуля в соревновании

`archparse` (Java, JavaParser, Jackson) — модуль статического анализа AST, извлекающий IR тел методов и JPA-сущностей:
1. `pool_ir.json` (`--pool all`) — плоский список веток и вызовов для списка методов `TargetPool` (ранний прототип M2).
2. `entity_ir.json` (`--mode entities`, `EntityScanner`) — сканер классов `@Entity`, `@Embeddable`, полей коллекций (R10) и конструкторов (R7).
3. `data/ir/<module>.json` (`--mode bodies`, `MethodIrWriter`) — полное дерево операторов и выражений для всех 1196 методов скелета по всем 42 сервисам. Именно его читает современный M4 (`engine/executor/interpreter.py`).

**Важно:** В итоговый архив сдачи `submission.zip` для проверяющей системы исходный код Java и `archparse` не упаковываются (`pack_submission.py`). Организаторам передаются готовые сгенерированные JSON-файлы в `code/data/`, а рантайм `run_eval.py` выполняется на чистом Python.

## 2. Замеры времени выполнения

Замеры проведены на рабочей машине разработчика под Windows:

| Режим / Команда | Время | Что делает |
|---|---|---|
| `gradlew.bat test` | 12.3 с | Запуск тестов JUnit, включая полный прогон `MethodIrWriterTest` |
| `gradlew.bat run --args="--pool all"` | 5.5 с | Парсинг методов из списка `TargetPool` в `data/pool_ir.json` |
| `gradlew.bat run --args="--mode entities"` | 9.4 с | Сканирование всех JPA-сущностей в `data/entity_ir.json` |
| `gradlew.bat run --args="--mode bodies"` | 11.1 с | Полный парсинг всех методов (1196) и привязка 8961 `call_site` в `data/ir/` |
| **Полный цикл пересборки** | **~26 с** | Последовательный прогон всех режимов с нуля |

## 3. Архитектурный аудит и Code Smells

1. **Хардкод пула методов в `TargetPool.java` (279 строк):**
   - Ручной список путей файлов и сигнатур методов (`CancelServiceImpl#cancelOrder`, `ExecuteServiceImpl#ticketExecute`...).
   - *Риск:* При проверке кода жюри это выглядит как жесткая подгонка под известные сценарии.
   - *Реальность:* Этот код относится только к legacy-режиму `pool_ir.json`. Современный M4 читает `data/ir/<module>.json`, построенный универсально для всех методов без ограничений пула.
   - *Решение:* Запланировано удаление `TargetPool` и `pool_ir.json` после отказа от legacy-пути движка (`TODO_universality_rules.md`).
2. **Дублирование парсеров тел методов (`AstAnalyzer` vs `BodyIrBuilder`):**
   - `AstAnalyzer.java` (496 строк) строит старый плоский список `BranchIR` / `CallIR`.
   - `BodyIrBuilder.java` (704 строки) строит иерархическое дерево выражений и операторов для `MethodIrWriter`.
   - Два класса решают смежные задачи разными моделями данных.
3. **Дублирование чтения и парсинга исходников:**
   - `MethodIrWriter.parseAll()` и `EntityScanner.parseAll()` независимо выполняют обход файлов `Files.walk(targetsDir)` и парсинг `StaticJavaParser.parse(p)`. При пересборке сотни Java-файлов парсятся дважды.
4. **Однопоточный парсинг AST:**
   - Все файлы компиляционных юнитов разбираются строго последовательно в одном потоке, не утилизируя многоядерные процессоры.

## 4. План оптимизации archparse (после работ по engine)

1. **Параллелизация разбора:**
   - Использование `parallelStream()` при чтении файлов ускорит разбор AST с 11 с до 2–3 с.
2. **Единый проход AST:**
   - Однократный разбор дерева `CompilationUnit` с передачей результата и в `EntityScanner`, и в `MethodIrWriter`.
3. **Очистка репозитория перед сдачей:**
   - Депрекация/удаление `TargetPool.java` и `AstAnalyzer.java`.
   - Подтверждение для организаторов: M2 полностью универсален и не содержит списка целевых классов.
