# Как дошли до 1.0: замер ячеек S2/S3 и сломанный `@PathVariable`

**Дата:** 19.10.2026
**Итог:** посылка 27 (ручной зонд) — **1.00000**; выдача кода после ветки `feature/82-unbound-path-variable` совпадает с ней ребро в ребро во всех восьми сценариях.
**Связано:** [code_record_drift.md](code_record_drift.md) (как код догнал 0.99457), [annotation_rules.md](../annotation_rules.md), правило R20.

## Исходная точка

Посылка 20 — выдача кода, 0.99457: S1, S4–S7 — 1.000, S2 и S3 — 0.981. До 1.0 — 0.0054.

Решение «S2 не хватает (2, 2, 1, 1), S3 — (1, 1, 1, 1), лишних рёбер нет» ([how_we_achieved_0_99457.md](../how_we_achieved_0_99457.md)) единственным не было. Перебором: если допустить до трёх ошибок каждого вида, баллам платформы соответствуют 319 сочетаний FP/FN в S2 и S3; если `remote` точен (замер 18.10: IoU 1.000 во всех семи, с тех пор `remote` не менялся) — 33. Отдельные рёбра подбирать было не по чему.

Поиск кандидатов «от скелета» тоже ничего не дал:

- методов, которых нет в идеальных сценариях: в S3 — 4 (типы страховки, подтверждены зондом 18), в S2 — 14 (перебронирование, отмена заказа обычного поезда);
- рёбер `data_access` скелета от исполненных методов вне ответа — только те, что правильно отсекают S0 и R10;
- невыбранных вызовов из исполненных методов 84 (S2) и 82 (S3), ни за одним нет SQL внутри сервиса;
- таблиц вне ответа в затронутых сервисах нет.

Вывод тогда: недостающее лежит не в ветках исполненных методов, а в том, чего мы не исполнили вовсе.

## Замер ячеек (посылки 21–26)

`scripts/probe_cells.py`: в каждой посылке из выдачи кода убран один вид рёбер в одном сценарии. Балл сценария падает на IoU вида / 4, итог — на IoU / 28. Итог платформа даёт с 6 знаками, но последний всегда 0: точность 1e-5, IoU ячейки известен с точностью ±2.8e-4. Для `data` (P ≈ 30) этого хватает на единственное решение; для `executes` и `calls` остаётся 2–3 кандидата, спорное снимает совместная проверка: шесть IoU вместе должны дать итог базы.

| | `executes` | `calls` | `data` |
|---|---|---|---|
| S2 | FN = 2, FP = 0 | 1 ошибка (вероятнее FN = 1) | FN = 2, FP = 0 |
| S3 | FN = 2, FP = 0 | 1 ошибка (вероятнее FN = 1) | FN = 2, FP = 0 |

Шесть посылок заменили 33 варианта одним.

## Диагноз

В S2 и S3 не хватало одного и того же: 2 метода, 1 вызов, 2 таблицы, `remote` не задет. Это форма одного входа шага через шлюз: контроллер (`executes` без входящего `calls`, R5), сервис (`executes` и `calls` из контроллера), SQL сервиса к двум таблицам. Единственный шаг, общий для S2 и S3 и отсутствующий в других сценариях, — шаг 4 «Browse the food stores at Suzhou station».

Шаг 4 M1 заземлял на `StationFoodController#getFoodStoresOfStation`. В коде у него ошибка:

```java
@GetMapping("/stationfoodstores/{stationId}")
public HttpEntity getFoodStoresOfStation(@PathVariable String stationName, ...)
```

Spring связывает `@PathVariable` по имени параметра (`stationName`), а в шаблоне `{stationId}`: `MissingPathVariableException` до вызова контроллера, метод не исполняется. Поэтому наши 4 ребра шага 4 были лишними (посылки 13–14 подняли балл, когда их убрали). По всему проекту такой обработчик один.

Рабочий обработчик того же контроллера, который принимает имя станции, — `POST /stationfoodstores` → `getFoodStoresByStationNames(List<String> stationNameList)` → `findByStationNameIn` и EAGER-коллекция. Через шлюз он даёт ровно 2 `executes`, 1 `calls`, 2 `data` (`station_food_store`, `station_food_list`); те же рёбра есть в идеальных S1 и S4, где его вызывает `getAllFood`.

Зонд 27 добавил эти 5 рёбер в S2 и S3 — **1.00000**.

## Что изменилось в коде

R20 «шаг — действие формы без запроса» (`engine/grounding/form_actions.py`, флаг `--form-only-steps`) удалён. Он давал верный результат на посылке 20 по неверной причине: шаг запрос шлёт, только сломанный обработчик до контроллера не доходит. Объяснение через сопоставление слов шага с `id` элементов формы было эвристикой.

Вместо него — правило Spring MVC (`engine/grounding/binding.py`, `StepGrounder.rebind`, флаг `--unbound-handlers rebind|keep`):

1. Обработчик, у которого имя `@PathVariable` (явное или имя параметра) не входит в переменные шаблона пути ни одного маршрута, Spring вызвать не может.
2. Если M1 выбрал такой обработчик, шаг идёт через обработчик того же класса, который Spring вызвать может и у которого есть параметр пути, query или тела с тем же корнем имени (`stationName` ↔ `stationNameList`). Если такой не один или его нет — замены нет.
3. Замена — после заземления: выбор M1 и история в промпте следующих шагов не меняются, кеш LLM цел. В `step_requests.json` у шага `grounding.rebound` с исходным обработчиком. Параметры не переносятся: значения тела M4 не нужны, чтобы исполнить `findByStationNameIn` и загрузку коллекции.

Флаги `--jackson-ctor` и `--lombok-tostring` остались ([code_record_drift.md](code_record_drift.md)).

Проверка: выдача `run_eval.py --executor ir --m4-unresolved-calls emit --no-server` совпадает с посылкой 27 по множествам рёбер во всех сценариях, S0 = 1.0; тесты — 343 прошли, падают 3 известных теста производительности.

## Что стоит запомнить

- **Сначала замер, потом кандидаты.** Шесть посылок по одной ячейке дали точные FP и FN и форму нехватки. Без этого искали бы в ветках исполненных методов, где ошибок не было.
- **Форма нехватки называет механизм.** «2 метода, 1 вызов, 2 таблицы, без `remote`» — это вход шага, а не ветка внутри сервиса.
- **Правило, верное по результату, может быть неверным по причине.** R20 «действие формы» сошёлся с посылкой 20, но прятал 5 рёбер. Объяснение надо проверять тем, что ещё из него следует.
- **Точность платформы — 5 знаков**, хотя показывает 6. Погрешность IoU ячейки — ±2.8e-4.
- **Фреймворк ломается статически проверяемо.** Несовпадение `@PathVariable` с шаблоном видно по скелету без запуска.
