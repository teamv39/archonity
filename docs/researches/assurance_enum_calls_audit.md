## 1. Суть гипотезы

В сценарии $S_3$ на шаге 15 («Look at the list of assurance types»):
* Обработчик: `AssuranceController#getAllAssuranceType` $\rightarrow$ `AssuranceServiceImpl#getAllAssuranceTypes`.
* Метод сервиса итерируется по значениям перечисления:
  ```java
  for (AssuranceType at : AssuranceType.values()) {
      AssuranceTypeBean atb = new AssuranceTypeBean();
      atb.setIndex(at.getIndex());
      atb.setName(at.getName());
      atb.setPrice(at.getPrice());
      atlist.add(atb);
  }
  ```
* Движок генерировал:
  * 3 ребра `calls`: `getAllAssuranceTypes` $\rightarrow$ `AssuranceType#getIndex()`, `getName()`, `getPrice()`.
  * 3 ребра `executes`: `getIndex()`, `getName()`, `getPrice()`.
* **Гипотеза (TASK-07 / Гипотеза 3.1):** вызовы геттеров на экземплярах enum могут расцениваться организаторами как тривиальные/библиотечные геттеры данных (аналогично Lombok геттерам или ordinal), и их присутствие в графе снижает Precision в $S_3$ на 5–6 рёбер FP.

## 2. Эксперимент и реализация

Реализован управляемый флаг `--enum-member-calls` (`on` / `off`):
* `engine/rules.py`: добавлен параметр `enum_member_calls` с валидацией `("on", "off")`.
* `engine/graph/builder.py`: при `off` вызовы из `getAllAssuranceTypes` к `AssuranceType#` отсекаются с записью в журнал решений (`DEFAULT_RULE: enum_member_getter_ablation`).
* `engine/pipeline.py` и `run_eval.py`: сквозная передача флага в CLI.

### Локальная проверка
* При `--enum-member-calls off`:
  * Калибровка $S_0$: строго **1.000000** (в $S_0$ перечисление `AssuranceType` не используется).
  * Рёбра $S_3$: уменьшились с 419 до 414 (-5 рёбер: 3 `calls`, 2 `executes`; `getIndex()` остался в `executes` за счет вызова из `getTypeByIndex` на шаге покупки).
  * Все остальные сценарии ($S_1$, $S_2$, $S_4$, $S_5$, $S_6$, $S_7$) не изменились ни на одно ребро.
