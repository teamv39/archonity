## 1. Контекст и статус

19 октября 2026 года в соревновании TECHARENA решением Archonity был достигнут максимальный результат **1.00000** (посылка 27 в ручном замере и посылка 28 в выдаче кода). Рекорд воспроизводится запуском `python run_eval.py -o output/submission.json` без дополнительных аргументов ребро в ребро во всех восьми сценариях (S0–S7).

В процессе достижения 1.00000 ключевое изменение затронуло правило **R20**:
1. Старая эвристика «действие формы без запроса» (`form_actions.py`) удалена: она давала правильный скор в посылке 20 по неверной причине, скрывая реальный сетевой запрос.
2. Внедрено правило спецификации Spring MVC: обработчик с несовпадающим именем `@PathVariable` (`{stationId}` в шаблоне пути vs `String stationName` в сигнатуре метода) отбрасывается, так как Spring DispatcherServlet выбрасывает `MissingPathVariableException` до вызова контроллера.
3. Добавлен механизм перепривязки (`binding.py`): при обнаружении такого обработчика шаг сценария перенаправляется на рабочий метод того же контроллера (`POST /stationfoodstores`), что вернуло недостающие рёбра в S2 и S3.

Что говорят организаторы: «решение одно — программа, которая по тексту **любого сценария** строит его блок»; код лучших решений перезапускают и проверяют на Local-First и статический анализ; бизнес-цель — легковесный анализатор для навигации ИИ-агентов по микросервисным проектам ([testing_system.md](../testing_system.md)). Требования работать на любом проекте Spring Boot в правилах нет. Универсальность за пределами Train Ticket — наша цель для проверки кода и защиты: подгонки под имена методов и 8 сценариев будут видны при чтении кода.

Ниже представлен детальный аудит актуального кода на предмет скрытых и явных подгонок под Train Ticket с оценкой рисков и рекомендациями по обобщению.

## 2. Анализ кодовой базы по слоям

### 2.1. Слой заземления M1 (`engine/grounding/`)

#### 1. Rebind несвязанного `@PathVariable`
* **Файл:** `engine/grounding/binding.py` (строки 29–82)
* **В чём специфика:**
  * Проверка `unbound_path_variables` универсальна: сверяет имена переменных `@PathVariable` с шаблоном маршрута `@GetMapping("/.../{id}")`.
  * Однако функция `rebind` содержит локальную эвристику: если найден сломанный обработчик, она ищет в том же контроллере метод с параметром похожего корня через `_stem` (`_stem("stationName") == _stem("stationNameList")`), подменяя `GET` на `POST` с пустым телом (`params={}`).
  * Spring сам запрос не перенаправляет: на `GET /stationfoodstores/{stationId}` он отвечает ошибкой до вызова контроллера. Фронтенд Train Ticket этот эндпоинт тоже не обходит: `POST /stationfoodstores` UI напрямую не вызывает вовсе, магазины станций он получает из `getAllFood` ts-food-service, который сам шлёт этот `POST` (в эталоне S2/S3 `getAllFood` нет, посылка 19). Эталон идёт прямым `POST` через шлюз — так выбрали запрос шага организаторы. `rebind` моделирует их выбор, а не поведение Spring или UI; правило выбора замены («тот же контроллер, тот же корень имени параметра») — эвристика, проверенная одним случаем.
* **Как должно быть в универсальном решении:**
  * Отсекать несвязываемый обработчик в каталоге M1 — правильно по смыслу, но **не сейчас**: индекс всех обработчиков входит в системный промпт выбора (`P.handler_index` в `StepGrounder.__init__`), ключ кеша LLM — sha256 полного текста сообщений. Любая правка каталога меняет промпт всех 103 шагов, кеш промахивается, нужен прогон на GPU, рекорд под риском.
  * Нет и гарантии, что модель выберет `getFoodStoresByStationNames`: среди кандидатов шага 4 выше него стоит `getFoodListByStationFoodStoreId` (тоже рабочий, тот же контроллер), рядом `getAllFoodStores`.
  * До пересборки кеша оставить `rebind` после заземления; при пересборке — убрать обработчик из каталога и проверить выбор модели по шагу 4 S2/S3.

#### 2. Текст системного промпта M1
* **Файл:** `engine/grounding/prompts.py` (строки 21–34)
* **В чём специфика:**
  * Константа `SYSTEM` содержит жестко зашитый доменный текст: *«You map steps of a user scenario in the Train Ticket web application...»*, *«Services come in twins for the two train kinds: high-speed trains (GaoTie/DongChe)... and regular trains...»*.
  * Модель прямо инструктируют о специфике китайских поездов и назначении сервисов `ts-*-other-service`.
* **Как должно быть в универсальном решении:**
  * Системный промпт должен быть абстрактным шаблоном для Spring Boot микросервисов.
  * Описание предметной области, назначение сервисов и правила разделения близнецов должны подаваться динамически через профиль проекта.

#### 3. Список сущностей для ссылок `REF_ENTITIES`
* **Файл:** `engine/grounding/request.py` (строки 9–10)
* **В чём специфика:**
  * `REF_ENTITIES = ("trip", "contact", "order", "food", "store", "station", "route", "train", "price", "consign", "assurance", "user")`.
  * Константа содержит ровно 12 сущностей предметной области Train Ticket.
* **Как должно быть в универсальном решении:**
  * Список допустимых сущностей для ссылок (`first_of_step_N`, `new_of_step_N`) должен формироваться автоматически из имен классов с аннотацией `@Entity` в анализируемом проекте.

#### 4. Удаление суффикса `other` в `twin_groups`
* **Файл:** `engine/grounding/retrieval.py` (строки 25–35)
* **В чём специфика:**
  * Функция `_norm_seg` удаляет подстроку `other` и цифры (`re.sub(r"other|\d+", "", s)`), чтобы объединять в группы близнецов `ts-order-service` и `ts-order-other-service`.
* **Как должно быть в универсальном решении:**
  * Близнецы должны группироваться по каноническим суффиксам версионирования API (`v1`, `v2`, `service1`, `service2`) либо по совпадению контрактов интерфейсов и DTO, без жесткой привязки к слову `other`.

### 2.2. Слой исполнения M4 (`engine/executor/step.py`)

#### 1. Доменные словари сущностей, ключей и полей
* **Файл:** `engine/executor/schema.py` (до 19.10 — `engine/executor/step.py`, строки 24–65)
* **Статус:** обобщено 20.10 (фаза A [ADR-007](../adr/adr-007_project_profile.md), раздел 8). Виды и ID-поля `EntitySchema` берёт из манифеста `engine/manifest.py` (23 вида из `@Entity`/`@Embeddable` скелета). Виды M1 v7 (`contact`, `price`, `consign`, `store`, `train`) переводятся в виды манифеста на входе шага, только в режиме `--ref-kinds v7`. Не тронуты по решению 20.10: `_FIELD_ALIASES`; список полей текущего пользователя `_USER_FIELDS` остался с обоснованием (раздел 8).
* **Было (до 20.10):** словари вынесены из `step.py` в `EntitySchema` (ветка `feature/84-step-executor-universality`), для 12 видов M1 — прежние значения `_DEFAULT_KIND_HINTS` и `_DEFAULT_ID_FIELDS`.
* **Что даёт поиск по скелету:** типы с `@Entity` (27) и поля с `@Id`/`@EmbeddedId` добавляют 20 новых видов (`waitlistorder`, `trainfood`, `money` и др.), но прежние не меняют. M1 на новые виды не ссылается, поэтому выдача та же (sha256 `94463c41…5a08`, проверено 19.10). Имена ID-полей новых видов собираются из имени класса в нижнем регистре (`traintypeId` вместо `trainTypeId`), с полями DTO они не совпадут. В списке отбрасываемых суффиксов имени класса есть доменное `order`.
* **В чём специфика:**
  * `_KIND_HINTS`: сопоставляет имена типов с 12 сущностями Train Ticket (`"train": ("traintype", "train")`, `"assurance": ("assurance",)`).
  * `_ID_FIELDS`: список первичных ключей (`orderId`, `tripId`, `contactsId`, `consignId`).
  * `_FIELD_ALIASES`: алиасы полей бронирования (`fromStation`, `startPlace`, `startStationName`, `travelDate`).
* **Что осталось:** виды ссылок задаёт схема ответа M1 (`REF_ENTITIES`), а она входит в ключ кеша LLM. Брать виды и ID-поля из скелета вместо прежних значений можно вместе с пересборкой кеша (Stage 0, [two_stage_pipeline_research.md](two_stage_pipeline_research.md)). Тогда же — имена ID-полей с исходным регистром (`<поле @Id>` или `<simpleName>Id`) и без доменных суффиксов.


#### 2. Синтетические дефолты в `build_dto`
* **Статус:** обобщено 20.10 (фаза A ADR-007, раздел 8): `m4-new-user`, `m4-new-contact-doc`, `m4-new-companion`, `13800000000`, `consignee`, `consignee-phone` убраны; значения — по правилам [annotation_rules.md](../annotation_rules.md), R21. Осталось с обоснованием: группа полей получателя багажа при весе 0.
* **Файл:** `engine/executor/step.py` (строки 272–302)
* **В чём специфика:**
  * При создании пользователя подставляется `userName = "m4-new-user"`.
  * При создании контакта подставляются китайский телефон `phoneNumber = "13800000000"`, `documentNumber = "m4-new-contact-doc"`, `name = "m4-new-companion"`.
  * При логине код подтверждения пустой: `defaults = {"verificationCode": ""}`. Это не подгонка, а условие организаторов: «no verification code at login» (`context/README.md`, поле `context` скелета) — его можно читать оттуда.
  * Для багажа `consigneeName` и `consigneePhone` ставятся, только если вес груза больше 0 (так делает UI `client_ticket_book.js`).
* **Как должно быть в универсальном решении:**
  * Генератор только по типам поля не заменит эти значения: они несут смысл для исполнения. Синтетическое имя пользователя нужно, чтобы шаг входа после регистрации (S4) нашёл ту же строку; уникальный номер документа — чтобы `ContactsServiceImpl#create` не нашёл дубликат (S3). Общие правила: (1) значение, которого нет в мире БД, для полей, по которым создающий метод ищет дубликат (`findBy<Поле>` перед `save`); (2) значение, записанное шагом, переиспользуется следующими шагами; (3) остальное — по типу.

#### 3. Нормализация станций в Retry Ladder
* **Файл:** `engine/executor/step.py` (строки 343–350, 482–489)
* **В чём специфика:**
  * `_is_place_param`: поиск подстрок `station`, `place`, `from`, `to`.
  * `_station_norm`: удаление пробелов и нижний регистр (`"Ning Bo" -> "ningbo"`) для согласования с форматом хранения в таблице `station`.
* **Как должно быть в универсальном решении:**
  * Исполнитель должен применять канонические сеттеры сущности (что уже реализовано в Jackson-fill) либо стандартную нормализацию строк `strip().lower()`.

#### 4. Проверка отказа обработчика `_is_failure`
* **Файл:** `engine/executor/step.py` (строки 491–500)
* **В чём специфика:**
  * Проверяется объект класса с именем `*.Response` и поле `status`, известное и не равное 1 — конвенция обёртки ответа Train Ticket (FQN не зашит).
* **Как должно быть в универсальном решении:**
  * В Spring Boot статус операции передается через `ResponseEntity.getStatusCode()`.
  * Для оберток ответов: обобщенная проверка полей `code == 200`, `success == true`, `error == null`.

### 2.3. Слой базы данных и AST-парсера (`world.py`, `archparse`)

#### 1. Приоритет модуля `ts-common`
* **Файл:** `engine/executor/world.py` (строки 88, 97)
* **В чём специфика:**
  * `for pref in (module, "ts-common"):` — поиск типа по FQN при неоднозначности явно отдает приоритет модулю `ts-common`.
* **Как должно быть в универсальном решении:**
  * Искать в текущем модуле, затем в модулях по маске `*common*`, `*shared*`, `*core*`, либо по графу зависимостей `pom.xml` / `build.gradle`.

#### 2. Доменные константы в AST-парсере `archparse`
* **Файлы:**
  * `archparse/.../config/TargetPool.java`: содержит 52 захардкоженных метода Train Ticket (рудимент режима M2 targets).
  * `archparse/.../enumres/EnumResolver.java:21`: `ORDER_STATUS_FQN = "edu.fudan.common.entity.OrderStatus"`.
  * `archparse/.../parser/TypeIndex.java:35`: `COMMON_WILDCARD_TYPES.put("OrderStatus", ...)`.
* **Как должно быть в универсальном решении:**
  * `TargetPool.java` — режим `--mode pool`, он же режим `Main.java` по умолчанию; из него собирается `data/pool_ir.json`, который `run_eval.py` подаёт в пайплайн через `ensure_pool_ir` (при отсутствии файла запускает Gradle). Выдача M4 от `pool_ir` не зависит: прогон с `ir_path=None` даёт тот же sha256 `94463c41…` (проверено 19.10). Удалять вместе с `ensure_pool_ir` и legacy-путём (OQ-10), иначе `run_eval.py` пойдёт пересобирать удалённый пул.
  * Резолюция перечислений должна работать по всем `enum`-типам проекта, найденным при обходе AST.

### 2.4. Слой Legacy-правил (`rules.py`, `state.py`, `builder.py`)

* **Файлы:** `engine/rules.py`, `engine/state.py`, `engine/graph/builder.py`
* **В чём специфика:**
  * `rules.py` содержит сотни строк с именами микросервисов `ts-*` (`ts-payment-service`, `ts-assurance-service`, `ts-travel2-service` и др.).
  * `state.py` содержит классы `OrderStatus` и `TrainType`.
  * `builder.py` содержит частные проверки `queryOrders` и `String2Date`.
* **Статус и влияние:**
  * **Неверно, что в режиме M4 эти участки не исполняются.** `pipeline.py` в режиме M4 вызывает `builder.apply_spring_security` (раздел 2.5); M3 (`engine/state.py`) передаётся в `StepExecutor.run_step` и разрешает ссылки шагов (`resolve_ref`, `account_id`, `user_name`); `ScenarioProfile` из `rules.py` строится на каждом шаге. Остальное в `rules.py` (эвристики отсева) и `builder.traverse` в M4 не исполняется.
  * Неактивный код всё равно создаёт шум и вопросы при проверке кода; удалять по OQ-10, сверяя sha256.

### 2.5. Пропущено в первой версии аудита (активно в M4)

#### 1. Spring Security из legacy-строителя
* **Файл:** `engine/graph/builder.py`, `apply_spring_security`; вызывается из `pipeline.py` и в режиме M4.
* **В чём специфика:** модуль аутентификации ищется по стандартному `loadUserByUsername` (общее), но вход — метод с именем из списка `getToken`, `authenticate`, `login`, а таблица пользователя — по подстроке `auth_user` или `user` в ID таблицы.
* **Как обобщить:** вход в аутентификацию — вызов `AuthenticationManager.authenticate` в IR исполненного метода; таблица — `data_access` метода `loadUserByUsername` в скелете.

#### 2. Модель состояния сценария M3
* **Файл:** `engine/state.py`; используется M4 через `resolve_ref`.
* **В чём специфика:** `OrderStatus` и `TrainType` повторяют перечисления Train Ticket; тип поезда выводится по префиксу номера (`G`/`D`) и по имени таблицы (`orders_other`).
* **Как обобщить:** коды статусов брать из перечислений проекта (`enum_codes` M1 их уже читает из исходников), тип «близнеца» — из группы близнецов M1 (`twin_groups`).

#### 3. Тип поезда по тексту сценария
* **Файл:** `engine/rules.py`, `ScenarioProfile.train_mode` (регулярные выражения по тексту: GaoTie, DongChe, regular); в `step.py` присваивается `self.it.train_mode`.
* **Статус:** в M4 значение больше нигде не читается (последний читатель — флаг абляции `security_check_scope` — удалён при очистке Category 1). Мёртвое присваивание: удалить вместе с `ScenarioProfile` из пути M4, сверяя sha256.
