# M4: откуда разница 0.93625 и 0.92539, и почему судья не меняет балл

**Дата:** 19.10.2026
**Сравниваются:** рекорд 0.93625 (наш M4, `dev` после PR #61) и 0.92539 (M4 Миши, ветка `feature/44-m4-executor`, коммит `988a6f7`, [разбор сдачи](m4_executor_score_0_92539.md)).
**Связано:** [OQ-05](../open-questions.md#oq-05), [OQ-12](../open-questions.md#oq-12), [OQ-13](../open-questions.md#oq-13), [m4_executor.md](m4_executor.md).

## Коротко

1. Посылки совпадают ребро в ребро на S0–S5 и S7. Вся разница — 31 ребро в S6, шаги 4 и 6: создание маршрута и рейса администратором.
2. Причина — имена станций ([OQ-12](../open-questions.md#oq-12)). M1 отдаёт `"Shanghai,Suzhou,Ning Bo"`, сервис ищет `shanghai,suzhou,ningbo`. Оба исполнителя честно получают отказ. Наш M4 видит, что шаг по тексту должен пройти, откатывает мир и повторяет шаг с именами в форме хранения (`--m4-success-retry`, ступень 1). У Миши повтора нет.
3. Отсюда баллы рекорда по сценариям: S1–S5 и S7 берём из сдачи Миши, S6 получается около 0.950.
4. Судья в `dev` выдачу не меняет: с судьёй и без неё она одинакова ребро в ребро. Это не поломка. Когда условие неизвестно, исполнитель берёт объединение обоих плеч, а это максимум рёбер. Судья может только отсечь лишнее, а на заданных ему вопросах лишнего не нашлось.
5. 63 обрезанных ответа — известная ошибка `m4-judge-v1`. В ветке Миши она исправлена в `m4-judge-v3`, но в `dev` попал `judge.py` версии v1.

## 1. Как сравнивали

Обе выдачи пересобраны из кеша, без GPU:

- Сравнение — множества `(relation, source, target)` по сценариям.

## 4. Судья в `dev`

### 4.1. Цифры прогона с кешем Миши (коммит `9c27cda`)

| | Значение |
|---|---:|
| Вопросов судье | 385 |
| Ответов из кеша | 322 |
| Вердиктов TRUE / FALSE | 111 / 182 |
| UNKNOWN | 29 |
| Без ответа (обрыв JSON, в кеш не попали) | 63 |
| Условий «оба плеча» | 92 |
| Решено правилом успешного пути | 18 |

Выдача с `--judge on` и с `--judge off` совпадает ребро в ребро на всех 8 сценариях. В журнале решений (`decisions.json`) нет ни одного ребра с источником `LLM_JUDGE`.

### 4.2. Почему так: контрфакт

Вердикты судьи подменялись прямо в прогоне (обёртка над `StepExecutor._ask_judge`, скрипт в приложении):

| Подмена | Изменение выдачи против `--judge off` |
|---|---|
| вердикт наоборот | S6 −97, S1 −3, S3 −3, S2 −1 |
| всегда TRUE | S6 −97, S1–S4 −1 (`RabbitReceive#process` → `delivery`) |
| всегда FALSE | S1, S3, S4 −2 (`Assurance#<init>`) |

Ни одна подмена не **добавила** ни одного ребра. Отсюда три вывода.

1. Судья решает условия, от которых рёбра зависят. Например, S6 −97 идёт от `TravelServiceImpl#afterToday`: стоит сказать «рейс в прошлом», и бронирование нового рейса рушится. Вывод агента Миши «условия, где плечи различаются по рёбрам, судье не доставались» неточен: доставались.
2. Без судьи такое условие идёт по обоим плечам, и рёбра объединяются (`run_arms`). Объединение — это максимум: любой выбор одного плеча даёт столько же рёбер или меньше.
3. На каждом таком условии судья выбрал плечо, которое и так давало максимум. По этим трём местам судья, судя по тексту сценариев, прав (рейс после сегодняшнего дня, страховка выбрана, доставка есть; построчно не сверялось), но выигрыша нет: объединение давало то же самое.

Итог: **при дефолте «оба плеча» судья поднимает балл, только если отсекает рёбра, которых на самом деле не было.** Среди его 385 вопросов таких мест нет.

Агент Миши прав в другом: 63 вопроса без ответа не важны. Даже «всегда TRUE» и «всегда FALSE» по всем вопросам, включая эти 63, задевают только три места выше, а их судья решил.

### 4.3. Обрыв JSON — ошибка v1, исправленная в v3

В `dev` лежит `engine/executor/judge.py` с `JUDGE_PROMPT_VERSION = "m4-judge-v1"`. В ветке Миши — `m4-judge-v3`, разница в схеме ответа:

```python
"cited_line": {"type": "string", "maxLength": 200},
"reasoning": {"type": "string", "maxLength": 400},
```

С ограничением длины ответ всегда помещается в лимит токенов клиента. Именно эта ошибка дала 63 обрыва (`Unterminated string…`). Правка из v2 (плечо `NO_EFFECT` в пройденном пути) к нашему адаптеру не относится: `StepExecutor._ask_judge` передаёт в путь только стек методов, без решений плеч.

### 4.4. Судья у Миши и у нас

Ядро Миши отдаёт судье 65 условий в 7 местах, наше — 385. Вопросов больше, потому что наш адаптер зовёт судью на каждом `if` с неизвестным условием, где правило успешного пути не сработало, в том числе в служебных методах вроде `StringUtils#String2Date` и `TravelServiceImpl#afterToday`. На S1–S5 и S7 выдачи совпадают, значит, рёбра, которые у Миши решает судья (багаж, код подтверждения, регистрация S4.1), наше ядро получает без него.

## 5. Куда двигаться дальше (судья, M1)

По убыванию пользы. Ожидаемый эффект указан честно: у первых двух пунктов он нулевой.

1. **Перенести схему v3 в `judge.py` в `dev`.** Это убирает 63 обрыва и делает кеш полным. На балл не влияет (раздел 4.2). Версия промпта меняется, поэтому кеш нужно собрать заново: 385 вопросов по 3 с — около 20 минут. Проверка — выдача не изменилась. **Схема перенесена 19.10** (`feature/64-judge-v3-schema`); кеш под v3 соберёт Миша.
2. **[OQ-12](../open-questions.md#oq-12) в M1: имена станций в форме хранения.** С нашим M4 на балл не влияет: повтор шага уже делает то же самое. Зато убирает костыль и защищает от падения S6 до 260 рёбер, если повтор когда-нибудь отключат или сломают. Проверка — с `--m4-success-retry off` выдача совпадает с рекордом.
3. **Сделать судью полезным: спрашивать там, где объединение может давать лишнее** ([OQ-13](../open-questions.md#oq-13)). Здесь лежит реальный прирост. Направления (не согласованы):
   - **Фильтр вопросов.** Спрашивать судью, только если у плеч разные рёбра скелета, с учётом вложенных вызовов. Из 385 вопросов на рёбра влияют единицы. Бюджет освободится под вопросы, которые судье сейчас не задают.
   - **Циклы, `switch`, тернарники.** Сейчас судья их не видит. Цикл по коллекции с неизвестным составом (R17) — кандидат на лишние рёбра: сколько их там, не мерили.
   - **Решения правила успешного пути** (18 условий) и отказы с `expected_outcome: refused` (S7). Там исполнитель угадывает ветку по форме кода, и ошибка стоит рёбер.
4. **Приоритет сценариев — S3 и S2** (0.913 и 0.919). Любую новую идею судьи сначала проверять на них.
5. **Перед каждой сдачей сравнивать выдачу с рекордом ребро в ребро.** Совпадает — сдача ничего не проверит. Так случилось с кешем судьи: прогон «с судьёй» дал ту же выдачу, что и без него.

## 6. Аудит исходов шагов (19.10)

Проверка: у каких шагов исход M4 (`Response.status`) противоречит `expected_outcome`. Из 103 шагов таких 5: S3.6 `createNewContacts`, цепочкой S3.8, S3.11, S3.13 и S7.8 `calculate` для заказа COLLECTED.

Причина S3.6: шаг передаёт только `documentType: 1`, а `findByAccountIdAndDocumentTypeAndDocumentType` с неизвестными `accountId` и `documentNumber` давал «любую подходящую строку», но не `null`. Поэтому `c != null` получался TRUE, и срабатывал ответ «Contacts already exists». Правка (`feature/73-s3-new-contact-cascade`): результат неточного поиска одной сущности без `Optional` помечается `maybe_null`, и сравнение с `null` даёт UNKNOWN, как уже было для `Optional`. После правки шаги S3 идут по тексту.

**Выдача не изменилась ни на одно ребро.** Рёбра ответа — множество по всему сценарию. Шаги 8, 11 и 13 повторяют шаги 7, 10 и 12 (бронь, открыть заказ, оплата) для второго пассажира и исполняют те же методы. Отказ шага 6 уже давал ребро `create → contacts` через поиск. В S6 повтор шага дал 31 ребро, потому что шаги 4 и 6 исполняют методы, которых в сценарии больше нет.

Вывод для гипотез: важен не исход шага сам по себе, а **рёбра, которые даёт только этот шаг**. Каскад отказов дорог, если ломает уникальные шаги, и бесплатен, если ломает повторы.

## Приложение: подмена вердиктов

```python
"""Контрфакт: CF_MODE = invert | true | false. Запуск: python cf_run.py <аргументы run_eval.py> --judge cache"""
import os, runpy, sys
sys.path.insert(0, os.getcwd())
from engine.executor import step as stepmod

MODE = os.environ["CF_MODE"]
orig = stepmod.StepExecutor._ask_judge

def patched(self, fr, stmt):
    v = orig(self, fr, stmt)
    if MODE == "invert":
        return None if v is None else (not v)
    return MODE == "true"

stepmod.StepExecutor._ask_judge = patched
sys.argv = ["run_eval.py"] + sys.argv[1:]
runpy.run_path("run_eval.py", run_name="__main__")
```
