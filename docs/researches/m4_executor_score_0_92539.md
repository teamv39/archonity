## Чем вторая сдача M4 отличается от первой

- В ветку влит `dev`. M1 на S2.14 выбирает `rebook` вместо `payDifference` (OQ-11), M3 получил реестр артефактов шагов.
- В M4 перенесены правила legacy из `dev`:
  - `station_food_collection=store_browse_only` — каталог магазинов станции идёт без таблицы блюд;
  - `element_callbacks` — `Order#equals` из `list.contains`.
- Тело `@RequestBody` между сервисами приводится к типу параметра обработчика.

S2 вырос на 0.066 (0.853 → 0.919). На шаге 14 M4 теперь проходит пересадку по ветке возврата разницы (`drawBackMoney`, `updateOrder`), а не доплату через `payDifference`, к этому добавился отсев `station_food_list` на шаге 4. Остальные сценарии изменились не больше чем на 0.007.

## Что видно по сценариям

- **S1, S4, S5, S7 — 0.938–0.951**, выше legacy от 17.10 на 0.024–0.048. Здесь работают решения IR по данным:
  - S5 — план travel-plan и выбор сервиса заказов по типу поезда;
  - S7 — бронирование распределяет место, `rebook` при статусе COLLECTED выходит рано;
  - во всех сценариях — багаж решает судья по тексту шага.
- **S6 — 0.874**, у legacy от 17.10 было 0.922. Это [OQ-12](../open-questions.md#oq-12): M1 отдаёт имена станций как в тексте (`"Shanghai,Suzhou,Ning Bo"`), сервисы хранят их без пробелов строчными. M4 честно уводит создание маршрута и поездки в отказ и теряет 12 методов против legacy. С нормализованными именами M4 покрывает всё, что даёт legacy, так что исправление M1 должно вернуть около 0.05 на S6.
- **S2, S3 — 0.913–0.919**, самые низкие после S6. Отдельно их не разбирали.

## Что проверить дальше

1. **OQ-12:** нормализовать имена станций в параметрах M1 для админских запросов (или при привязке запроса в M4) и сдать.
2. **Гипотеза R2:** рёбра к `TripId#toString` по фактическому типу объекта (по 6 рёбер на сценарий, 11 в S5). Сдача с `--m4-no-runtime-type-edges` ([OQ-07](../open-questions.md#oq-07)).
3. **Исполнитель по умолчанию.** M4 обгоняет legacy, можно делать `--executor m4` умолчанием в `run_eval.py` (решение команды, ADR-005).
