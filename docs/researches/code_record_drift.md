**Дата:** 19.10.2026
**Сравниваются:** выдача `dev` на `40bb11e` (`run_eval.py --executor ir --m4-unresolved-calls emit --no-server`) и ручная посылка 17 ([eval/records/](../../eval/records/README.md)).
**Итог:** разница — 18 рёбер, все объясняются тремя механизмами. Прототипы всех трёх вместе дают рекорд ребро в ребро во всех восьми сценариях, S0 = 1.0.
**Статус:** реализовано в ветке `feature/81-code-matches-record` (флаги `--jackson-ctor`, `--lombok-tostring`, `--form-only-steps`, правила R7, R5, R20 в [annotation_rules.md](../annotation_rules.md)). Выдача кода = посылка 17 ребро в ребро. Отличия от прототипов: Jackson-конструктор исполняется и в принимающем сервисе межсервисного вызова (выдачу не меняет); действие формы сопоставляется по словам `id`/`name` элемента, без слов виджета.

## 1. Jackson исполняет конструктор тела запроса

`RebookInfo` (тело `RebookController#rebook`) — `@Data`, но конструктор без аргументов написан руками и вызывает метод проекта:

```java
public RebookInfo(){
    ...
    this.date = StringUtils.Date2String(new Date());
}
```

Jackson создаёт тело запроса этим конструктором. По R7 ([ADR-006](../adr/adr-006_constructor_visibility.md)) способ создания не важен: из конструктора исполнился вызов проекта, значит, конструктор и ребро из него есть в ответе, ребра в него нет. В коде этого нет: `StepExecutor.build_dto` собирает DTO сразу полями, конструктор не исполняется.

Причина пропуска в коде двойная: `build_dto` не зовёт конструктор, и вдобавок `handler_args` вызывается до `run_handler`, который создаёт sink шага. Событие, записанное в `build_dto`, теряется.

**Прототип:** в `run_handler`, после события входа и до вызова обработчика, исполнить конструктор без аргументов у каждого `@RequestBody`-типа (только рукописный, узел скелета). Отбор делает существующая проекция R7. Результат: конструкторы 15 тел запросов исполняются по всем сценариям, проекция оставляет только `RebookInfo` в S2 и S7. Лишних рёбер нет. Обход вложенных DTO выдачу не меняет.

**Что учесть в реализации.** Прототип исполнял конструктор на отдельном объекте и значения не переносил. Правильнее: значения конструктора — умолчания, поля из тела запроса их перекрывают (так делает Jackson). Это может сдвинуть ветки (например, `date` у `RebookInfo` станет известной), поэтому после правки — сравнение с рекордом. Флаг для абляции. Запись в R7 и R8.

## 2. Lombok-`toString` при логировании

`BasicServiceImpl.java:118` и `:319` логируют результат через `{}`:

```java
BasicServiceImpl.LOGGER.info("[queryForTravel][all done][result: {}]", result);
```

SLF4J форматирует аргумент через `toString()`. У `TravelResult` он сгенерирован Lombok (`@Data`) и по умолчанию берёт поля через геттеры, если они есть. `isStatus()` написан руками, поэтому исполняется. Ребра `calls` нет (R5: вызывает библиотека). Уровень логов — INFO по умолчанию Spring Boot: своих `logback`/`logging.level` в сервисах нет, так что `info`/`warn`/`error` форматируются, `debug` — нет. Механизм — H1 из [слепой разметки](../../eval/blind/notes.md).

**Прототип:** в `eval_call` для `info`/`warn`/`error` у приёмника `LOGGER`/`logger`/`log` с литералом `{}` обойти аргументы как Lombok-`toString`: класс с `@Data`/`@ToString`/`@Value` (аннотации есть в узлах `type` скелета), собственные нестатические поля, рукописный геттер (`is`/`get`) — исполнить, вложенные объекты, списки и словари — рекурсивно. Рукописный `toString` — исполнить вместо обхода.

Результат: `isStatus()` во всех семи сценариях, других изменений нет. Остальные срабатывания (`TripId#toString`, `TripInfo#getStartPlace`/`getEndPlace`, `TripAllDetailInfo#getFrom`/`getTo`, `LeftTicketInfo#toString`) уже были в ответе другими путями. Вариант с явным `x.toString()` выдачу не меняет.

**Что учесть.** Флаг для абляции. Запись в R5: фраза «неявного `toString` у `TripId`/`LeftTicketInfo` на путях не найдено» устарела.

## 3. Шаг 4 в S2/S3: действие формы без запроса

В UI единственный запрос о еде — `getAllFood` при открытии страницы бронирования (`client_ticket_book.js:40`, `initFoodSelect`). Магазины станций приходят в его ответе (`foodStoreListMap`), выбор станции — `onchange="preserveChangeFoodStation()"` у `#food-station-list` — работает по этой карте, без запроса. `StationFoodController#getFoodStoresOfStation` UI не вызывает нигде. Бэкенд запрос не отсёк бы: маршрут в шлюзе есть, Security — `permitAll`.

Простое правило «нет запроса в UI — нет запроса в эталоне» неверно. Шаги без запроса в UI (`eval/m1_steps.json`, статус `no_ui`) дают уникальные рёбра в S1.9, S1.14, S4.1, S4.10, S5.5, S7.8–10, а эти сценарии в рекорде равны 1.000: там эталон запрос шлёт, обработчик выбран по коду сервиса. Шаг 4 отличается тем, что действие в UI **есть**, но это элемент формы без запроса.

Локальных действий (обработчик `onchange`/`onclick` из HTML без AJAX, в том числе через вызываемые функции) в активном UI пять, все на странице бронирования: `needFoodOrNot`, `changeFoodType`, `preserveChangeFoodStation`, `preserveChangeFoodStore`, `needConsignOrNot`. По пересечению слов с текстами шагов S0–S7 на них похожи только S2.4, S3.4 и сами шаги бронирования. Шаги бронирования отпадают по первому условию ниже: их обработчик (`preserve`) UI вызывает.

**Предлагаемое правило (после заземления, M1 не меняется):** шаг не шлёт запроса, если

1. выбранный M1 обработчик не вызывается ни одним запросом UI (каталог `ui_catalog.py`), и
2. текст шага соответствует локальному действию формы — обработчику события без AJAX.

Почему после заземления: история шагов входит в промпт M1 (`history_block`). Если менять заземление шага 4, изменятся промпты всех следующих шагов S2 и S3, кеш LLM промахнётся, нужен прогон на GPU. Правило после заземления оставляет кеш как есть. Его же стоит позже перенести в M1, когда будет пересборка кеша.

**Что учесть.** Каталог UI сейчас читает только `onclick` и аналоги: `onchange` надо добавить. Сопоставление с текстом — BM25 по словам функции, `id` элемента и надписи, порог подбирать так, чтобы сработали только S2.4 и S3.4; прототип — пересечение слов, этого мало для кода. Владелец M1 — Миша.

## Как воспроизвести

Прототипы — обёртки над `run_eval.py` по методике [agent_lessons.md](../agent_lessons.md), раздел 4. Лежат в `scripts/drift/`, пайплайн не меняют, запуск из корня репозитория:

| Скрипт | Что делает |
|---|---|
| `wrap_jackson_ctor.py` | механизм 1 (`JACKSON_NESTED=1` — и вложенные DTO) |
| `wrap_lombok_tostring.py` | механизм 2 (`LOMBOK_EXPLICIT=1` — и явный `toString()`) |
| `wrap_all.py` | все три механизма, шаг 4 убирается напрямую (замер, не правило) |
| `local_actions.py` | локальные действия UI и похожие на них шаги |
| `unique_noui.py` | уникальные рёбра шагов без запроса в UI |

```powershell
$env:PYTHONUTF8=1; python scripts/drift/wrap_all.py --executor ir --m4-unresolved-calls emit --no-server -o <папка>/submission.json
python scripts/compare_submissions.py <папка>/submission.json eval/records/submission_p17_0.99457.json --show 50
```

Ожидаемый вывод: все восемь сценариев «совпадают».
