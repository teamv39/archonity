# M4: исполнитель по IR тел методов

**Дата:** 18.10.2026
**Ветка:** `feature/52-m4-ir-executor`
**База:** посылка 0.924310 (legacy, `dev` на b48e096; выдача `dev` совпадает с ней ребро в ребро)

## 1. Что сделано

Исполнитель по ADR-005 (M4) — пакет `engine/executor/`, включается флагом `run_eval.py --executor ir` (нужен `--grounder m1`, он по умолчанию). Без флага всё как было: legacy-обход скелета, выдача не изменилась ни на одно ребро.

| Файл | Что делает |
|---|---|
| `values.py` | Значения: конкретные, `UNKNOWN`, объекты, списки и множества, Optional, даты, строки с дырами (URL). Трёхзначная логика и слияние значений двух путей. |
| `world.py` | Мир сценария: форк дампа БД и типы из скелета. Строка таблицы превращается в объект сущности (`@Column`, встраиваемые типы, enum по порядковому номеру, коллекции в отдельных таблицах), объект — обратно в строку при `save`. Производные запросы Spring Data и простые нативные `@Query`. |
| `interpreter.py` | Обход тел методов из `data/ir`. Цели вызовов — из скелета (`calls`, `runtime_dispatch`, CHA, `target` IR для R7). RestTemplate — выбор обработчика по URL и HTTP-методу (R3) и вход в него. Репозиторий — запрос к миру и ребро `data`. |
| `library.py` | Модели JDK, Spring и Lombok: геттеры и сеттеры, String, числа и BigDecimal, Optional, коллекции и стримы, итераторы, JSON (Jackson, fastjson), Date/Calendar/SimpleDateFormat, DecimalFormat, UUID, `@Builder`. |
| `step.py` | Шаг: аргументы обработчика из `StepRequest` (params, refs), реестр результатов шагов, перенос событий в журнал решений. |
| `judge.py` | Судья LLM для условий UNKNOWN (модуль Миши, см. раздел 8): кеш `cache/llm/`, бюджет вызовов, по умолчанию выключен (`--judge on`). |

Состояние сценария (заказ и его статус, баланс, созданные сущности) M4 не берёт из ручных мутаций M3, а получает исполнением: заказ, созданный покупкой, на следующих шагах находится по своему ID, оплата меняет статус через `modifyOrder`, возврат при отмене пишет сумму `280.00` в `inside_money`. От M3 остаётся только начальный пассажир.

## 2. Решения по семантике

Каждое правило сформулировано через Java, Spring, JPA или контекст скелета, а не через имена сценариев.

1. **Условие UNKNOWN.** Сначала успешный путь: если одно плечо кончается отказом (`throw`, `return new Response<>(статус != 1, ...)`, `x.setStatus(0); return x;`, `return null`), а другое нет, исполняется второе — кроме шагов, где M1 ожидает отказ. Затем судья (если включён). Иначе оба плеча; мутации полей и списков в каждом плече изолированы, после плеч значения сливаются. Объекты, созданные внутри плеча, не откатываются.
2. **Цикл** по пустой точной коллекции не исполняется (R17), по неизвестной — один раз. `catch` — только при исключении (R15), лямбда — когда её вызывает библиотека (R16).
3. **Неточный запрос к БД** (условие с UNKNOWN) возвращает «неизвестную строку»: наличие и поля неизвестны. Первая строка таблицы под видом найденной давала ложные отказы.
4. **MySQL**: сравнение строк в запросе без учёта регистра (collation `*_ci`). Java-`equals` и `HashMap` остаются точными.
5. **Jackson** заполняет DTO через сеттеры: рукописный `Station.setName` нормализует имя (`Ning Bo` → `ningbo`). Рёбер такой вызов не даёт (вызов библиотекой через отражение исключён в REFERENCE).
6. **Часы системы** — 15.09.2026 15:30 (контекст скелета, покупки прогрева в 15:00). `new Date(y, m, d, ...)` с годом от 1900, как в Java.
7. **Логин** — пассажир из контекста скелета (`fdse_microservice`, без кода подтверждения) или пользователь, зарегистрированный в сценарии. Текущий пассажир — `userId` из ответа логина.
8. **Создание через POST** (`create*`, `add*`, `register*`, `save*`, `insert*`): собственный ID новой сущности клиент не присылает (`null`).
9. **Багаж**: UI ставит имя, телефон и вес получателя только при отмеченном «need consign» (`client_ticket_book.js`). Вес из шага есть всегда, имени нет, поэтому вес 0 даёт `consigneeName = null`, вес больше 0 — непустое имя.
10. **Ссылки `refs`**: `new_of_step_n` — сущность, сохранённая шагом n; `first`/`second` — элемент ответа шага n (вид — по имени типа или по ID-полю, `TravelAdvanceResultUnit.tripId`). Если у шага n нет своей сущности этого вида — та, на которую ссылался сам шаг n (M1 называет заказ «заказом шага оплаты»). Поля DTO берутся из сущности, её вложенных объектов и параметров шага, на который ссылаемся (дата и станции поиска).
11. **Повтор шага** (`--m4-success-retry`, по умолчанию on). Шаг по тексту успешен, а по значениям M1 отказал — значит, LLM восстановила строку не в той форме, которую принял бэкенд. Мир откатывается, шаг повторяется: ступень 1 — названия станций в форме хранения Train Ticket, ступень 2 — словесные строки неизвестны, ступень 3 — все строки неизвестны. Срабатывает только в S6 (шаги 4 и 6: `Shanghai` против `shanghai` в `HashMap` проверки станций).

Решение «поля вне тела UI-запроса — `null`» проверено и отклонено: UI оплаты не шлёт `userId`, тогда оплата всегда шла бы внешним каналом, а тексты S1–S3, S5–S7 прямо говорят «from the internal account balance». Гарнитура организаторов отправляла больше полей, чем UI.

## 3. Результат: паритет и расхождения

S0 — 1.0000 (65/65), как у legacy. S1–S5 совпадают с legacy ребро в ребро. Отличаются 19 рёбер в S6 и S7, каждое объяснено по коду.

| Сценарий | Рёбра | Что и почему |
|---|---|---|
| S6 | −8 | Новый рейс G9101: заказов на него нет, `OrderServiceImpl#getSoldTickets` уходит в `else` (`Order is Null`), `LeftTicketInfo#<init>`, `#toString`, `Ticket#<init>` не исполняются; `SeatServiceImpl#distributeSeat` пропускает блок `if (leftTicketInfo != null)` с `isContained`. |
| S7 | +10 | Шаг 4 — успешная покупка, `PreserveServiceImpl#dipatchSeat` реально распределяет место (`SeatController#create`, `distributeSeat`, `Ticket#<init>`, `isContained`, `getTicketListByDateAndTripId`). ## 4. Гипотеза M4-1: вызовы с неразрешённым получателем

`trip.getTripId().toString()` в `BasicServiceImpl#queryForTravels`, `TravelServiceImpl#getTicketsByBatch`, `#setResponse` — явные вызовы проектного `TripId#toString` (и из него `Type#getName`). В скелете у этих call_site нет ребра: тип получателя в цепочке не разрешён. REFERENCE определяет `calls` как «вызывающий метод → действительно вызванный метод», то есть по исполнению. По умолчанию (`--m4-unresolved-calls mute`) M4 считает значение, но рёбер не пишет; `emit` пишет их: +6 рёбер в S1–S4 и S7, +11 в S5, +3 в S6 (по 2 `executes` и 3–9 `calls`).

## 8. Мерж с `dev` и судья Миши (18.10)

Ветка `feature/60-m4-dev-merge-judge` от тега `m4-ir-0.93625` (архив `output/archives/saved/m4-ir-0.93625.zip`), в неё влит `dev` (PR #52–57).

- Исполнитель Миши (WIP из PR #52: `executor.py`, `interp.py`, `program.py`, `refs.py`, `repo.py`, `defaults.py`, `facts.py`) и `tests/test_m4_parity.py` удалены: в той же папке теперь этот исполнитель, а `--executor m4` — синоним `--executor ir`. Его выдача на платформе — 0.91411; расхождения с нашей разобраны по рёбрам (`Order#equals`, `station_food_list` на шаге 4, багаж «без багажа», рейс S6, старый кеш M1 для S2.14).
- Судья — `engine/executor/judge.py` Миши без изменений: промпт с исходником метода, кеш `cache/llm/`, режимы `on`/`cache`/`off`, бюджет вызовов сервера. Исполнитель зовёт его на условии UNKNOWN после правила успешного пути и собирает `JudgeQuery` в `StepExecutor._ask_judge`: путь — стек методов, факты — известные значения кадра, состояние — пассажир и его заказы в мире M4. Флаги `run_eval.py --judge on|cache|off` (по умолчанию off) и `--judge-budget` (400).
- Обобщения `dev` (#53–57) приняты: legacy-выдача после мержа совпадает с посылкой 0.924310, M4 с `--m4-unresolved-calls emit` — с архивом 02 (0.93625) ребро в ребро на всех 8 сценариях.
- Прогон с судьёй без сервера: 399 вопросов, 0 попаданий в кеш (кеш Миши записан под промпты его исполнителя), выдача не меняется. Проверка судьи — на машине с `llama server`: `python run_eval.py --executor ir --m4-unresolved-calls emit --judge on`, затем ответы из `cache/llm/` коммитятся, архив собирается из кеша с `--no-server`.
