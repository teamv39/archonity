# Аудит решений движка по S2 и S3

> **Архив, 17.10.** Аудит legacy-движка на балле 0.918, до исполнителя M4 и ADR-006. Текущий остаток S2/S3 — [roadmap.md](../roadmap.md).

**Дата:** 17.10.2026
**Вывод:** ветки и вызовы внутри исполненных методов движок решает верно. Искать потери S2 (0.873) и S3 (0.875) там бессмысленно, это проверено. Причина в том, чего движок не моделирует.

## Что проверено

Инструмент — журнал решений (`engine/decisions.py`, `output/decisions.json`, отчёт `scripts/decision_log.py`). Журнал совпадает с ответом ребро в ребро, это проверяет тест.

1. **Риск A: рёбра ответа без проверенных условий** (S2: 264, S3: 229). Во временной копии archparse в пул поставлены все 226 вызывающих методов из риска A по S1–S7 (4264 вызова, 100% совпадение со скелетом). Результат:
   - S2: 236 из 264 рёбер стоят вне условий; если метод выполнился, вызов тоже выполнился. S3: 199 из 229.
   - Условные рёбра (S2: 25, S3: 26) проверены по коду и по `context/db-after-warmup.sql.gz`, все включены верно:
     - `getSoldTickets` и `isContained`: на 1 октября в БД есть заказы на Z1234 (`orders_other`, S2) и D1345 (`orders`, S3), ветка «билеты уже проданы» выполняется.
     - `InsidePaymentServiceImpl#pay`: у пользователя `fdse_microservice` пополнений 10 361 (`inside_money`), платежей 1 670 (`inside_payment`). Оплата идёт с внутреннего баланса.
     - `drawBack`: `findByUserId` возвращает список, а не `null`, ветка возврата выполняется всегда.
     - Остальное: циклы по непустым результатам поиска и по enum, для нового заказа нет записи еды и страховки, `status == 0 :else` — успешный путь.
2. **Риск B: рёбра, срезанные `rules.py`** (S2: 18, S3: 8). Все срезы верны по коду: проверка кода при входе, `/welcome`, внешняя оплата, страховка и консайн, сервисы скоростных поездов для обычного поезда, смена типа поезда при перебронировании, уведомление при отмене.
3. **Контрольный опыт.** Прогон движка с полным IR (276 методов, R7, R15–R17 и правила веток на всех исполненных методах) выдачу не изменил ни в одном сценарии, S0 = 1.0000. Расширение пула с 34 до 52 методов тоже дало ноль.
4. **Резолвер.** Шаги S2 и S3 привязаны к правильным обработчикам, тип поезда определяется верно на каждом шаге.

## Чего не делать

- Расширять пул archparse в расчёте на балл S2/S3. Новые ветки либо «ошибка, ранний выход», либо уже решены правилами.
- Перепроверять G/D-диспатч, опции заказа, баланс и проданные билеты в S2/S3: проверено выше.

## Где искать дальше

Журнал видит только рёбра, которые движок рассматривал. Пропущенные рёбра и неверная разметка в нём не видны. Кандидаты:

1. **Рёбра вне скелета:** методы, которые вызывает фреймворк (Jackson, слушатели RabbitMQ, ленивая загрузка JPA), таблицы коллекций (`route_stations` и т. п.).
2. **Механизмы, которых нет в S0.** S2/S3 состоят в основном из покупки, оплаты, отмены, перебронирования, MQ-рассылки еды. В эталоне S0 их нет, поэтому правила разметки для них ничем не подтверждены. Следующий шаг: разбить рёбра S2/S3 по механизму и сверить с `annotation_rules.md` те, что в S0 не встречаются.

## Как повторить

- Журнал: `$env:PYTHONUTF8=1; python scripts/decision_log.py --scenarios S2 S3`.
- Полный IR: дописать во временную копию `TargetPool.java` методы из `risk_skeleton_included` (отчёт `decision_log.py -o`), собрать IR с `-o` во временный файл и передать его в `ArchonityPipeline(ir_path=...)`. Сравнить `submission.json` с обычным прогоном.
