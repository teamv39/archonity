## 2. Калибровка на S0

Сначала разметить S0 тем же способом, что S3 (раздел 3), не открывая эталон. Потом проверить:


## 3. Как размечать

По каждому шагу S3 по порядку:

1. **Запрос.** Найти в `ts-ui-dashboard`, какой HTTP-запрос шлёт UI на это действие, и какой обработчик проекта его принимает. Если UI запроса не шлёт, обработчик берётся по коду сервиса (REFERENCE: каждый шаг — один запрос). Параметры — из текста шага и сценария.
2. **Исполнение.** Пройти код обработчика построчно с конкретными данными: параметры шага, строки дампа БД, всё, что изменили прошлые шаги (созданные заказы, контакты, статусы, баланс). Для каждого `if`, цикла, `switch`, тернарника записать значение и откуда оно известно. Если значение по данным не выводится, решить по тексту шага (ожидаемый исход «успех» или «отказ») и пометить решение как допущение.
3. **Рёбра.** По `annotation_rules.md` записать `executes`, `calls`, `remote`, `data` для того, что действительно выполнилось. ID — дословно из `nodes` скелета, новых не придумывать. Правила со статусом «гипотеза» применять, но помечать.

Важно:

- Лишнее ребро стоит столько же, сколько пропущенное. Ребро, которое достижимо, но не выполнилось, не ставится.
- `remote` идёт от метода с вызовом `RestTemplate` к обработчику другого сервиса. Внутренний вызов того же сервиса — это `calls`.
- `data` — от метода, где стоит вызов репозитория, к каждой таблице, к которой ушёл SQL, включая таблицы коллекций.
- Лямбда исполняется, только если её вызвали. Тело цикла — только если коллекция непуста.

## 4. Что сдать

Ветка `feature/<id>-blind-s3` от `dev`, коммит и пуш, PR не открывать.

- `eval/blind/S0.json`, `eval/blind/S3.json` — формат как у `submission.json`:
  ```json
  {"project": "trainticket", "scenarios": {"S3": {"edges": [
    {"source": "scenario:S3", "relation": "executes", "target": "method:..."}
  ]}}}
  ```
- `eval/blind/S3_trace.md` — трасса по шагам: обработчик, решения веток со значением и источником (`файл:строка`), допущения, отказы.
- `eval/blind/notes.md` — итог калибровки S0, спорные места REFERENCE и `annotation_rules.md`, правила, которые пришлось уточнить.

Проверка формата перед сдачей:

```bash
cd hackaton/tt-challenge
python platform/evaluate_golden.py gold/S0.json ../../eval/blind/S3.json
```

(балл S0 тут не важен; для S3 проверяются формат, существование ID и виды вершин).

## 5. Что делаем потом (основная сессия)

`scripts/compare_submissions.py output/submission.json eval/blind/S3.json --scenario S3` — расхождения по видам рёбер. Каждое расхождение относим к шагу и решению из трассы и смотрим, кто прав по коду. Если неправ исполнитель, ищем механизм, а не правку под шаг: правка должна сдвинуть рёбра хотя бы в нескольких местах или сценариях. Если неправ разметчик — уточняем задание.
