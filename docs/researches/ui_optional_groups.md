# Поля под условием UI: как подгонка прошла сторож и чем её заменили

22.10.2026, PR #149. Статус — действует.

## Что случилось

На перефразированном S5.8 («…no meal, no assurance and no consignment») M4 пошёл в ветку оформления багажа: лишние `createConsign`, `insertConsign`, цена багажа, −0.035 к баллу S5. Тот же дефект — в своём X8.4.

Причина — правило M4 в `build_dto`: имя и телефон получателя багажа становились `null`, только если M1 явно передал `consigneeWeight <= 0`. Веса нет — имя неизвестно, условие `consigneeName != null` в `preserve` не решено, M4 идёт в обе ветки.

Первая правка (коммит `3280c71`) добавила «нет ни имени, ни телефона, ни веса — тоже `null`». Балл вырос, рекорд цел, сторож литералов зелёный. Но правило — подгонка: имена полей `consigneeName`, `consigneePhone`, `consigneeWeight` записаны в коде движка (Python и Rust), на другом проекте оно не сработает. Подгонкой было и исходное правило «вес 0» в рекорде.

## Почему сторож не поймал

`tests/test_no_project_literals.py` искал маркеры проекта: имена сервисов (`ts-…`), пакеты (`fudan`, `fdse`), `trainticket`, UUID пассажира. Имена полей DTO под маркеры не подпадают. Проверка Rust к тому же смотрела только `archonity-parse`, а не `archonity-m4` и `archonity-exec`.

## Чем заменили

Знание о группе полей есть в самом проекте — в коде формы UI:

```js
if ($('#need-consign-or-not').is(":checked")) {
    orderTicketInfo.handleDate = currentdate;
    orderTicketInfo.consigneeName = $("#name_of_consignee").val();
    ...
}
```

Каталог UI (`engine/grounding/ui_catalog.py`) уже выделял такие поля (`body_opt`: поле, каждое присваивание которого стоит под общим условием) и литералы под условием (`body_cond`: `foodType = 2` внутри «еда выбрана»). Не хватало одного шага — донести это до M4.

- `UIRequest.body_groups()` — поля `body_opt`, сгруппированные по общему условию, и литералы `body_cond` под тем же условием. Каталог на диске и карточки M1 не меняются, ключи кеша LLM целы.
- `StepRequest.body_groups` — новое поле контракта M1 → M4 (Python и Rust, `step_requests_raw.json`).
- M4 (`build_dto`): группа отправлена, если в параметрах шага есть её поле или литерал условия со значением не по умолчанию. Иначе полей в запросе нет, у DTO — умолчание Jackson (`default_value`: `null`, 0, `false`, инициализатор поля).
- Значение по умолчанию признаком не служит: Jackson дал бы его и без поля. Поэтому «вес 0» и `isWithin: false` не говорят, что флажок отмечен, и старое правило «вес 0» стало частным случаем общего.

Флаг — `--ui-optional-groups on|off`; `off` — правила нет вовсе.

## Сторож

`test_engine_has_no_project_field_names`: имена полей и классов из скелета проекта, встреченные строковым литералом в `engine/`, `run_eval.py` и `rust/crates/*/src` (вне `#[cfg(test)]`), — либо общее слово (`GENERIC`: `id`, `name`, `type`, …), либо известный долг с причиной (`KNOWN`), иначе тест падает. Долг из `KNOWN`, который больше не встречается, тоже роняет тест: список не зарастает.

Найденный долг, оставлен с причиной:

- `accountId`, `userId`, `loginId` — поля тела, куда UI кладёт ID вошедшего пользователя (`schema._USER_FIELDS`). Общее правило — поток данных UI (`sessionStorage.setItem("client_id", …)` → `accountId: sessionStorage.getItem("client_id")`), но каталог не хранит нелитеральные значения полей. Следующий кандидат на ту же замену.
- `username` — контракт Spring Security `UserDetails#getUsername`, не проекта.
- `balance` — свой ключ контекста пассажира из текста сценария, с полем проекта совпадает случайно.

Отдельно `test_engine_rust_has_no_project_literals`: маркеры Train Ticket теперь проверяются во всех crate, а не только в `archonity-parse`.

## Границы

- Списки `GENERIC` и `KNOWN` ручные: сторож делает новое имя проекта в коде заметным, но не решает за человека, общее ли это слово.
- Имена методов проекта сторож не проверяет — только поля и классы.
- Правило работает там, где у обработчика есть запрос в каталоге UI. Нет UI (R20, прямой вызов API) — групп нет, поля как раньше неизвестны.
- `canon_value` для дробей пишет Python-`repr` (`pyfmt::float_repr` в Rust); значения вида `1e-05` в литералах UI не встречаются, но паритет на них не проверен.

## Вывод на будущее

Правило M4, которое называет поле, класс или значение проекта, — подгонка, даже если оно описывает настоящий механизм. Сначала искать этот механизм в артефактах проекта (скелет, IR, каталог UI, дамп): часто нужные данные уже собраны и просто не доведены до места применения, как `body_opt` здесь. Зелёный сторож литералов не доказывает универсальность — он ловит только то, что умеет искать.
