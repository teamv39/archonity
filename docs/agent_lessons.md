## 2. Арифметика балла

Балл — среднее по 28 ячейкам (7 сценариев × 4 вида рёбер), в каждой IoU. В сценарии около 180 `executes`, 200 `calls`, 35 `remote`, 35 `data`.

- Одно ребро `calls` или `executes` стоит около **0.0002** итогового балла, одно `remote` или `data` — около **0.001**.
- Разрыв 0.064 — это грубо 30 ошибочных рёбер на сценарий.
- Гипотеза про один шаг правит 1–5 рёбер и даёт ±0.001. Заметный прирост давали только механизмы, которые правят десятки рёбер или все сценарии сразу:

  | Что | Прирост |
  |---|---|
  | R10, ленивые коллекции | +0.015 |
  | M4: повтор шага с именами станций в форме хранения (S6) | +0.011 (+0.076 на S6) |
  | R2 `emit`: вызовы с неразрешённым в скелете получателем | +0.007 |
  | M4 вместо legacy | +0.005 |
  | Заземление `rebook` на S2.14 | +0.004 |

- **Ответ — множество рёбер по всему сценарию.** Шаг ценен только теми рёбрами, которых не дают другие шаги. Пример: S3.6–13 шли в отказ, после правки пошли по тексту, а выдача не изменилась ни на одно ребро — шаги 8, 11 и 13 повторяют методы шагов 7, 10 и 12. В S6 те же отказы стоили 31 ребро, потому что шаги 4 и 6 уникальны.

## 3. Что подтверждено — не перепроверять

По эталону S0 (балл 1.0), REFERENCE или отдельной посылке. Подробно — [probe_edge_classes.md](researches/probe_edge_classes.md).

- Рёбра скелета из исполненных методов берутся почти все. Исключения S0 совпадают с нашими: `user_roles` из `loadUserByUsername`, конструктор исключения, которое не бросалось, `JWTUtil` (R9), `String2Date` в невыполненной ветке, `verifyCode`.
- Геттеры с телом, утилиты, контроллеры, сервисы — S0.
- Методы enum, включая вызов через константу (`OrderStatus.PAID.getCode()`) — S0.
- Spring Security: в каждом сценарии те же 8 рёбер `executes`, что в S0 (`User#getPassword`, `isEnabled`, `JWTFilter#doFilterInternal`…).
- R7 в режиме `project_calls` — S0 и платформа; режим `body` опровергнут (0.8842). `--entity-ctors off` убирает рёбра, которые есть в эталоне S0 (S0 падает до 0.90).
- Посылками: R10 (+0.015), R13 RabbitMQ (абляция −0.009), `Order#equals` из `list.contains` (+0.0012), `station_food_list` на шаге 4, R2 `emit`, `rebook` на S2.14. Статусы остальных гипотез пула — таблица в [next_day_hypotheses_and_todo.md](researches/next_day_hypotheses_and_todo.md).
- Неочевидное: тексты сценариев «from the internal balance» опровергают правило «поля вне тела UI-запроса — null» (UI оплаты не шлёт `userId`).

Единственный крупный класс, по которому S0 молчит, — конструкторы DTO и сущностей без `@Entity` через `new` (275 рёбер). REFERENCE их прямо включает.

**Вывод:** разрыв сидит не в правилах разметки, а в отдельных решениях исполнения: какая ветка, сколько итераций цикла, что в состоянии. Следующий шаг — [слепая разметка S3](researches/blind_annotation_task.md).

## 4. Методика

Каждая проверка — до посылки, а не вместо неё.

1. **Сравнить выдачу с рекордом ребро в ребро:** `python scripts/compare_submissions.py A.json B.json --show 20 --decisions <decisions.json прогона A>`. Не изменилось ничего — посылка ничего не проверит. Изменилось больше, чем ждали, — сначала разобраться.
2. **Перед зондом прогнать флаг и посмотреть, что он убирает.** Вилка в таблице классов — гипотеза, а прогон показывает, что флаг меняет на самом деле. Пример: R7 по таблице выглядел перспективно, а флаг убирал рёбра, подтверждённые S0.
3. **Классы рёбер:** `python scripts/probe_edge_classes.py <submission> <decisions> [--by origin]` — размер класса, кандидаты вне ответа, сигнал S0, вилка сдвига балла.
4. **Аудит исходов шагов:** у каких шагов ответ обработчика (`_is_failure`) противоречит `expected_outcome`. Стоит делать после правок исполнителя, но помнить пункт про уникальные рёбра (раздел 2). Запуск — обёртка над `StepExecutor.run_step`, как ниже.
5. **Контрфакт:** подменить решение (вердикт судьи, исход шага, значение) обёрткой и посмотреть, двигается ли выдача. Так за один прогон видно, может ли механизм вообще влиять на балл.
6. **Трассировка веток:** печать условия и окружения в нужном методе.

```python
# Обёртка для пунктов 4–6: запуск как python wrap.py <аргументы run_eval.py>
import os, runpy, sys
sys.path.insert(0, os.getcwd())
from engine.executor import interpreter as im

orig = im.Interpreter.exec_if
def exec_if(self, s, fr):
    if "ContactsServiceImpl" in fr.method:
        print(fr.method, s.get("line"), im.tri(self.eval(s["cond"], fr)), file=sys.stderr)
    return orig(self, s, fr)
im.Interpreter.exec_if = exec_if
sys.argv = ["run_eval.py"] + sys.argv[1:]
runpy.run_path("run_eval.py", run_name="__main__")
```

Другие точки для обёрток: `StepExecutor._ask_judge` (вердикт судьи), `StepExecutor.run_step` (исход шага, `self.results[n]`).

## 5. Судья M4

- На неизвестном условии исполнитель без судьи идёт по обоим плечам и объединяет рёбра. Объединение — максимум: любой выбор одного плеча даёт столько же рёбер или меньше. Поэтому судья может поднять балл, **только отсекая** рёбра, которых не было.
- На 385 вопросах из кеша Миши выдача с судьёй и без него совпала ребро в ребро. Подмена вердиктов только убирает рёбра (S6 −97, если сказать «рейс в прошлом»).
- Куда двигать судью — [OQ-13](open-questions.md#oq-13): спрашивать только там, где плечи различаются рёбрами; циклы, `switch`, тернарники; решения правила успешного пути и отказы.

## 6. Устройство M4, которое легко пропустить

- **Повтор шага** (`--m4-success-retry`): шаг по тексту успешен, а исполнитель получил отказ — мир откатывается, шаг повторяется с ослабленными строковыми параметрами. Несущая конструкция S6: без неё S6 теряет 189 рёбер.
- **Неточный поиск в БД.** `findBy…` с неизвестными параметрами: для `Optional` — `maybe`, для сущности — `maybe_null`, сравнение с `null` даёт UNKNOWN. `maybe_null` пока только в ветке `feature/73-s3-new-contact-cascade` (выдачу не меняет); в `dev` такой поиск возвращает строку и никогда не `null`.
- **Исход шага.** Правило успешного пути (`arm_fails`) работает только при `expected_outcome != refused`. Оно смотрит на форму плеча (throw, `Response` со статусом не 1, `return null`), а не на данные.
- Атрибуция в `decisions.json`: у ребра остаётся первая причина, с которой оно появилось (`Sink.edge` — `setdefault`), а вызванный метод исполняется в своём кадре со своей причиной. Поэтому отсутствие `LLM_JUDGE` или `DEFAULT_RULE` в журнале не значит, что судья или правило ни на что не влияли: судья, например, влияет через возвращаемые значения (`afterToday`). Проверять контрфактом.

## 7. Чего не делать

- Не подбирать эталон посылками по отдельным рёбрам: сигнал одного ребра около 0.0002, и это уже чтение скрытого ответа. Зонды — только по классам и только флагом в коде ([probe_edge_classes.md](researches/probe_edge_classes.md), раздел 4).
- Не выдавать изменение без эффекта на выдачу за улучшение: называть прямо.
- Не упаковывать посылку без свежего прогона: `pack_submission.py` выдачу не пересчитывает.
