# AGENTS.md — Archonity

## О проекте
**Archonity** — инструмент статического анализа и графового ML для реконструкции семантического графа runtime-зависимостей микросервисной архитектуры по исходному коду и конфигурациям. Целевая метрика — **IoU** по направленным типизированным рёбрам.

Архитектура и детали пайплайна — в /adr

## Жёсткие ограничения
* **Только статический анализ:** запрещено собирать, запускать или инструментировать анализируемый проект в рантайме.
* **Strict Local-First:** запрещены любые вызовы внешних облачных API (OpenAI, Anthropic и др.). Все модели и парсеры работают строго локально.
* **Точность графа:** направление и тип каждого ребра критичны для метрики IoU.
* **Правило БД:** обращения разных микросервисов к одной таблице БД — отдельные независимые рёбра от каждого сервиса к узлу таблицы.
* **Фильтрация под рантайм:** в итоговый граф попадают только связи, достижимые из публичных точек входа (контроллеры, слушатели очередей, cron-задачи).

## Контракты данных
* Все парсеры пишут выходные данные строго в типизированный формат `facts.json` (узлы, `inbound_endpoints`, `outbound_calls`, `db_access`, `internal_call_graph`).
* Любое добавленное в итоговый граф ребро обязано иметь запись в `evidence.json` с указанием источника (`AST_EXACT`, `CONFIG`, `ML_PREDICTED`), файла/строки и веса уверенности `confidence`.

## Как работать

Решения принимает пользователь, агент предлагает и аргументирует.

ВАЖНО: КАЧЕСТВО > СКОРОСТЬ/КОЛИЧЕСТВО! 

1. Перед правкой — прочитай затрагиваемые файлы (Read, не угадывай).
2. Обсуди подход с пользователем до реализации: выбор подхода, библиотеки, структуры, контракта, изменение скоупа — всё, что трогает архитектуру. Если доступен скилл `/grill-me` — используй его; если нет — задавай вопросы по одному с рекомендацией и вариантами.
3. Не выдавай предположение за согласованное решение. Итог обсуждения фиксируй в ADR или issue.
4. Работай в ветке `feature/<id>-kebab` от `dev`. Не пушь в `main`/`dev` напрямую.
5. Правь доки и код в одном PR/коммите, если меняешь поведение.
6. Не расширяй скоуп молча. Нашёл проблему шире задачи — скажи одной фразой, продолжай в рамках скоупа.
7. Не генерируй код без опоры на принятые ADR.
8. Мелочи (опечатки, форматирование, очевидные правки) — делай без обсуждения.

## Стиль

- Язык доков — русский, стиль — коротко и по-человечески.
- Без эмодзи, без пафоса, без декоративного юникода.
- Диаграммы — `mermaid` (flowchart). ASCII-бокс только для деревьев директорий. Проверяй рендер.
- Сохраняй бренды в цитатах/коде/путях как есть.

## Git

- `dev` — основная рабочая ветка. `main` — стабильная, обновляется только из `dev`.
- Ветки: `feature/<id>-kebab` от `dev`, мерж обратно в `dev`.
- **Агент не пушит в `main` и `dev` напрямую.** Только в свою feature-ветку.
- **Перед мержем агент запрашивает ревью у пользователя:** показывает `git diff --stat`, краткое описание изменений, затем ждёт явного "ок". Молчание или "посмотрю позже" — не аппрув.
- Мерж `dev` → `main` — только по явной команде пользователя.
- Коммиты: `type: что сделано` (например `docs:`, `feat:`, `fix:`).
- Перед пушем: `git status`, `git diff --stat`.

## Чек-лист перед мержем

- [ ] Работа в `feature/<id>-kebab`, цель мержа — `dev`
- [ ] Дока обновлена вместе с кодом
- [ ] Коммит маленький, сообщение понятное
- [ ] Пользователь посмотрел изменения и явно разрешил мерж

Безопасный дефолт без вопроса — только для мелочей в рамках задачи; скажи, что предположил. Не блокируйся молча.
