# AGENTS.md — Archonity

## О проекте
**Archonity** — лёгкий статический анализатор, который по тексту сценария пользователя, исходникам и графу-скелету предсказывает исполнение сценария в микросервисном проекте (Train Ticket): какие методы выполнятся (`executes`), кто кого вызовет (`calls`), какие запросы уйдут в другие сервисы (`remote`) и к каким таблицам уйдёт SQL (`data`). Метрика — среднее **IoU** по четырём видам рёбер на каждый сценарий.

Пайплайн — [ADR-005](./docs/adr/adr-005_scenario_execution_pipeline.md), видимость конструкторов — [ADR-006](./docs/adr/adr-006_constructor_visibility.md). Правила разметки эталона — [annotation_rules.md](./docs/annotation_rules.md). Состояние и план — [roadmap.md](./docs/roadmap.md).

## Жёсткие ограничения
* **Только статический анализ:** запрещено собирать, запускать или инструментировать анализируемый проект и собирать по нему рантайм-данные.
* **Strict Local-First:** запрещены любые вызовы внешних облачных API (OpenAI, Anthropic и др.). Модели и парсеры работают локально.
* **Только исполненное:** в ответ сценария попадает только то, что выполнилось при данных этого сценария, а не всё достижимое из точек входа. Лишнее ребро стоит столько же, сколько пропущенное.
* **ID из скелета:** концы рёбер — ID методов и таблиц из `nodes` скелета, дословно. Новые ID не придумываем.
* **Правило БД:** ребро `data` идёт от метода, в котором стоит вызов репозитория, к каждой таблице, к которой ушёл SQL (включая таблицы коллекций). Разные методы и сервисы дают отдельные рёбра.
* **Воспроизводимость:** ответы LLM кешируются в репозиторий; прогон из кеша без GPU даёт тот же `submission.json`.

## Контракты данных
Описаны в [ADR-005](./docs/adr/adr-005_scenario_execution_pipeline.md):
* `StepRequest` — шаг сценария, сопоставленный с обработчиком и параметрами.
* IR тел методов (`ir/<module>.json`) — выход `archparse`.
* `submission.json` — формат организаторов.
* `evidence.json` v2 — у каждого ребра ответа есть запись: шаги, источник (`SKELETON`, `IR_BRANCH`, `IR_CALL`, `STATE`, `DEFAULT_RULE`, `FRAMEWORK_RULE`), правило, файл/строка, `confidence`.

## Выдача кода и рекорд

Выдачу кода даёт запуск без дополнительных флагов:

```powershell
$env:PYTHONUTF8=1; python run_eval.py -o <папка>/submission.json
```

Конвейер один: M1 (заземление шагов) → M4 (исполнение по IR) → правило Spring Security → M5 (проекция). Legacy-обход скелета, режимы отката и судья M4 удалены 21.10 (PR #110). Умолчания флагов — конфигурация рекорда (`--m4-unresolved-calls emit`, `--ctors caller_only`, `--jackson-ctor on`, `--lombok-tostring on`, `--unbound-handlers rebind`, `--embed-model on`). Без ключей выдача совпадает с рекордом 1.0 байт в байт (sha256 в [eval/records/](./eval/records/README.md)). LLM и эмбеддинги берутся из `cache/`: сервер не нужен. На промахе кеша `run_eval.py` сам поднимает `llama-server` и грузит эмбеддер из `models/` ([docs/run_on_a100.md](./docs/run_on_a100.md)).

Финальный запуск у организаторов (Linux, A100 40 ГБ) — одна команда, она докачивает модели по `models/manifest.json` и сверяет sha256:

```bash
scripts/run_final.sh <файлы сценариев>   # без аргументов — S0–S7
```

Архив посылки — `python pack_submission.py` после прогона в `output/`: в корне `submission.json` и `RUN.md` с командами, в `code/` код, кеши, зависимости и манифест моделей.

Промпт M1 — без слов домена: домен и правила близнецов из профиля проекта, виды ссылок из манифеста сущностей ([ADR-007](./docs/adr/adr-007_project_profile.md)). Правка промпта или карточек M1 меняет ключи кеша `m1-v8`: пересборка — на GPU (`scripts/start_llm.ps1`), после неё сверять выдачу с рекордом. Шаг S2.14 держится на ничьей голосов (ADR-007, «Хрупко»). В коде нет литералов Train Ticket, кроме умолчаний путей входа к пакету задачи: это проверяет `tests/test_no_project_literals.py`.

Лучшая посылка платформы — в [eval/records/](./eval/records/README.md). Рекорд может быть ручной правкой `submission.json`, тогда выдача кода от него отличается (roadmap, «Где мы»). Любую правку до посылки сравнивать с рекордом ребро в ребро: `scripts/compare_submissions.py`. Результаты посылок — таблица в roadmap.

## Как работать

Решения принимает пользователь, агент предлагает и аргументирует.

ВАЖНО: КАЧЕСТВО > СКОРОСТЬ/КОЛИЧЕСТВО! 

0. Перед запуском тестов и скриптов обязательно ознакомься с [environment_guide.md](./docs/environment_guide.md) во избежание типовых ошибок окружения (кодировка консоли Windows, запуск Gradle, допустимые отклонения в perf-тестах).
1. Перед правкой — прочитай затрагиваемые файлы (Read, не угадывай).
2. Обсуди подход с пользователем до реализации: выбор подхода, библиотеки, структуры, контракта, изменение скоупа — всё, что трогает архитектуру. Если доступен скилл `/grill-me` — используй его; если нет — задавай вопросы по одному с рекомендацией и вариантами.
3. Не выдавай предположение за согласованное решение. Итог обсуждения фиксируй в ADR или issue.
4. Работай в ветке `feature/<id>-kebab` от `dev`, в отдельном worktree: в основной папке одновременно работают другие агенты ([environment_guide.md](./docs/environment_guide.md), раздел 9). Не пушь в `main`/`dev` напрямую.
5. Правь доки и код в одном PR/коммите, если меняешь поведение.
6. Не расширяй скоуп молча. Нашёл проблему шире задачи — скажи одной фразой, продолжай в рамках скоупа.
7. Не генерируй код без опоры на принятые ADR.
8. Мелочи (опечатки, форматирование, очевидные правки) — делай без обсуждения.

## Стиль

- Язык доков — русский, стиль — коротко и по-человечески.
- Без эмодзи, без пафоса, без декоративного юникода.
- Диаграммы — `mermaid` (flowchart). ASCII-бокс только для деревьев директорий. Проверяй рендер.
- Сохраняй бренды в цитатах/коде/путях как есть.

## Git

- `dev` — основная рабочая ветка. `main` — стабильная, обновляется только из `dev`.
- Ветки: `feature/<id>-kebab` от `dev`, мерж обратно в `dev`.
- **Агент не пушит в `main` и `dev` напрямую.** Только в свою feature-ветку.
- **Агент коммитит и пушит в свою feature-ветку сразу**, без отдельного согласования, чтобы изменения видела вся команда. Правки по ревью — следующими коммитами в ту же ветку, без переписывания истории (`--amend`, force-push).
- **Изменения идут через PR в `dev`.** Агент открывает PR после первого пуша (`gh pr create --base dev`).
- **Мерж PR — только после явного "ок" пользователя:** агент показывает `git diff --stat` и краткое описание. Молчание или "посмотрю позже" — не аппрув.
- Мерж `dev` → `main` — только по явной команде пользователя.
- Коммиты: `type: что сделано` (например `docs:`, `feat:`, `fix:`).
- Перед пушем: `git status`, `git diff --stat`.

## Чек-лист перед мержем

- [ ] Работа в `feature/<id>-kebab`, ветка запушена, PR открыт в `dev`
- [ ] Дока обновлена вместе с кодом
- [ ] Коммит маленький, сообщение понятное
- [ ] Пользователь посмотрел изменения и явно разрешил мерж
